Ansible rescue Keyword

The rescue section allows you to execute recovery tasks when a task inside an Ansible block fails. It is used to handle errors and perform corrective actions instead of immediately stopping the automation workflow.

1. What Is rescue?

In the previous lesson, you learned how to group tasks using the block keyword.

A block can contain several tasks. If one of those tasks fails, Ansible normally stops executing the remaining tasks in that block.

The rescue section provides an alternative execution path. When a task inside the block fails, Ansible skips the remaining normal tasks in that block and executes the tasks defined under rescue.

2. Basic Syntax

---
- name: Demonstrate rescue
  hosts: ansible-client
  become: true

  tasks:
    - name: Application deployment
      block:
        - name: Execute operation
          ansible.builtin.command:
            cmd: /bin/false

      rescue:
        - name: Handle failure
          ansible.builtin.debug:
            msg: "The operation failed. Executing recovery tasks."

The playbook contains two main sections:

  • block: Contains the normal tasks.
  • rescue: Contains the recovery tasks executed when a block task fails.

3. Understanding Execution Flow

Consider a block containing three tasks: 

tasks:
  - name: Application deployment
    block:
      - name: First task
        ansible.builtin.debug:
          msg: "First task executed"

      - name: Second task
        ansible.builtin.command:
          cmd: /bin/false

      - name: Third task
        ansible.builtin.debug:
          msg: "Third task executed"

    rescue:
      - name: Recovery task
        ansible.builtin.debug:
          msg: "Recovery executed"

The execution order is:

Order Task Result
1 First task Executed successfully
2 Second task Failed
3 Third task Skipped
4 Recovery task Executed

Once the second task fails, Ansible skips the remaining normal tasks inside the block and moves to the rescue section.

4. Example: Handle a Failed Application Operation

Imagine that an application deployment command fails. Instead of stopping immediately, you want to display a recovery message. 

---
- name: Application deployment recovery
  hosts: ansible-client
  become: true

  tasks:
    - name: Deploy application
      block:
        - name: Execute deployment command
          ansible.builtin.command:
            cmd: /bin/false

        - name: Display deployment success
          ansible.builtin.debug:
            msg: "Application deployed successfully"

      rescue:
        - name: Display deployment failure
          ansible.builtin.debug:
            msg: "Deployment failed. Recovery process started."

Because the deployment command fails:

  • The deployment command is marked as failed.
  • The success message task is skipped.
  • The rescue section executes.
  • The recovery message is displayed.

5. Perform Actual Recovery Operations

The rescue section is not limited to displaying messages. You can perform actual corrective operations.

For example, if an application directory is missing, you can create it as part of the recovery process. 

---
- name: Recover application directory
  hosts: ansible-client
  become: true

  tasks:
    - name: Application preparation
      block:
        - name: Check application directory
          ansible.builtin.command:
            cmd: test -d /opt/application
          changed_when: false

        - name: Display directory status
          ansible.builtin.debug:
            msg: "Application directory exists"

      rescue:
        - name: Create missing application directory
          ansible.builtin.file:
            path: /opt/application
            state: directory
            mode: '0755'

        - name: Display recovery result
          ansible.builtin.debug:
            msg: "Application directory created during recovery"

If the directory does not exist, the check task fails and the rescue section creates the directory.

The directory creation task is an actual recovery operation, not just a status message.

6. Access Failure Information Inside rescue

Ansible provides information about the failed task through the special variable ansible_failed_task.

You can use this variable to identify which task failed. 

---
- name: Display failed task information
  hosts: ansible-client
  become: true

  tasks:
    - name: Application operation
      block:
        - name: Execute operation
          ansible.builtin.command:
            cmd: /bin/false

      rescue:
        - name: Display failed task name
          ansible.builtin.debug:
            msg: "Failed task: {{ ansible_failed_task.name }}"

The variable ansible_failed_task contains information about the task that triggered the rescue section.

You can also access the result of the failed task using ansible_failed_result. 

- name: Display failure details
  ansible.builtin.debug:
    msg: "Return code: {{ ansible_failed_result.rc }}"

For command tasks, the return code is available through ansible_failed_result.rc.

Important: These special variables are available inside the rescue section for handling the failure. The attributes available depend on the module that failed.

7. What Happens After rescue Succeeds?

When all tasks in the rescue section complete successfully, Ansible considers the original block failure to have been handled. The play can continue with subsequent tasks. 

---
- name: Continue after recovery
  hosts: ansible-client
  become: true

  tasks:
    - name: Application operation
      block:
        - name: Execute failing operation
          ansible.builtin.command:
            cmd: /bin/false

      rescue:
        - name: Handle failure
          ansible.builtin.debug:
            msg: "Failure handled successfully"

    - name: Continue automation
      ansible.builtin.debug:
        msg: "Automation continued after recovery"

The execution flow is:

  1. The command fails.
  2. The rescue section executes.
  3. The recovery task succeeds.
  4. The next normal task executes.
Important: A successful rescue does not mean the original operation succeeded. It means Ansible considers the failure handled and allows the play to continue. The original task remains failed in the execution history.

8. What Happens If rescue Also Fails?

If a task inside the rescue section fails, Ansible normally marks the play as failed for that host and stops executing subsequent tasks for that host. 

---
- name: Demonstrate rescue failure
  hosts: ansible-client
  become: true

  tasks:
    - name: Application operation
      block:
        - name: Original operation
          ansible.builtin.command:
            cmd: /bin/false

      rescue:
        - name: Recovery operation
          ansible.builtin.command:
            cmd: /bin/false

    - name: Task after recovery
      ansible.builtin.debug:
        msg: "This task will not execute if rescue fails"

Both the original operation and the recovery operation fail. Therefore, the final task is not executed.

9. Important Rules About rescue

  • rescue must be associated with a block.
  • Rescue tasks execute when a task inside the block fails.
  • Remaining normal tasks in the failed block are skipped.
  • Rescue tasks execute sequentially.
  • ansible_failed_task identifies the failed task.
  • ansible_failed_result provides the failed task result.
  • If rescue succeeds, Ansible allows the play to continue.
  • If rescue fails, the failure is not considered recovered.
Important limitation: Rescue does not handle every possible failure. Unreachable hosts and invalid task definitions, such as syntax errors, do not trigger the rescue section in the same way as ordinary task failures.

10. Practical Lab: Recover From an Application Deployment Failure

Scenario

You are deploying an application on ansible-client. The deployment operation fails. Your playbook must create a recovery directory, record the failure details, and continue with the remaining automation.

Create this playbook:

---
- name: Application deployment recovery lab
  hosts: ansible-client
  become: true

  tasks:
    - name: Application deployment
      block:

        - name: Execute application deployment
          ansible.builtin.command:
            cmd: /bin/false

        - name: Display deployment success
          ansible.builtin.debug:
            msg: "Application deployment completed"

      rescue:

        - name: Create recovery directory
          ansible.builtin.file:
            path: /opt/application-recovery
            state: directory
            mode: '0755'

        - name: Record failed task
          ansible.builtin.copy:
            content: |
              Failed task: {{ ansible_failed_task.name }}
              Return code: {{ ansible_failed_result.rc }}
            dest: /opt/application-recovery/failure.log
            mode: '0644'

        - name: Display recovery message
          ansible.builtin.debug:
            msg: "Recovery information recorded"

    - name: Continue automation
      ansible.builtin.debug:
        msg: "Automation continued after recovery"

Run from ansible-controller:

ansible-playbook application-recovery.yml

Expected behavior:

  • The application deployment command fails.
  • The rescue section executes.
  • The recovery directory is created.
  • The failure details are written to /opt/application-recovery/failure.log.
  • The recovery message is displayed.
  • The final task executes because rescue succeeds.

Why Do We Use the Ansible rescue Keyword?

In real DevOps environments, automation can fail during application deployment, configuration management, package installation, or infrastructure provisioning. Simply stopping the playbook may leave the environment in an incomplete state.

The rescue keyword provides a recovery mechanism. When a task inside a block fails, Ansible can execute corrective operations such as creating missing directories, recording failure details, restoring configuration, or performing cleanup.

For example, if an application deployment fails, a rescue section can record the error, prepare a recovery directory, and perform the necessary corrective actions.

This makes automation more resilient because the playbook can respond to expected operational failures instead of immediately abandoning the workflow.

However, rescue should not hide critical failures. Recovery tasks must perform meaningful corrective actions, and the automation must still make the failure visible to operators.
