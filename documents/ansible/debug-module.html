Ansible Debug Module

The Ansible Debug module displays messages, variable values and task results during playbook execution. It is commonly used for troubleshooting, verifying variables and understanding what is happening inside a playbook.

1. What Is the Debug Module?

The ansible.builtin.debug module prints information during playbook execution. It does not modify files, install packages or change the configuration of a managed host.

Common use cases include:

  • Displaying variable values.
  • Displaying registered task results.
  • Printing custom messages.
  • Inspecting Ansible facts.
  • Troubleshooting playbook execution.
  • Verifying values before performing subsequent tasks.

2. How Does the Debug Module Work?

             Ansible Controller
             ------------------
                    |
                    v
                Playbook
                    |
                    v
              Execute Task
                    |
                    v
              Debug Module
                    |
                    v
          Display Message or Variable
                    |
                    v
             Ansible Output

The Debug module displays information in the Ansible execution output. It is executed as part of the playbook on the controller, even though the play targets managed hosts.

3. Important Debug Parameters

Parameter Description
msg Displays a custom message. This is the default parameter.
var Displays the value of a variable.
verbosity Controls the minimum Ansible verbosity level required to display the debug task.

4. Display a Simple Message

Use the msg parameter to print a custom message.

Playbook: debug-message.yml

---
- name: Display a message
  hosts: ansible-client
  become: true

  tasks:
    - name: Display welcome message
      ansible.builtin.debug:
        msg: "Welcome to Ansible automation"

5. Display Variables Using Debug

You can display variables defined in the playbook using the var parameter.

Playbook: debug-variable.yml

---
- name: Display variables
  hosts: ansible-client
  become: true

  vars:
    application_name: learning-labs
    application_port: 8080
    environment: production

  tasks:
    - name: Display application name
      ansible.builtin.debug:
        var: application_name

    - name: Display application port
      ansible.builtin.debug:
        var: application_port

    - name: Display environment
      ansible.builtin.debug:
        var: environment
Important: When using var, write the variable name without {{ }}. Ansible evaluates it automatically.

6. Display Multiple Variables in One Message

You can use Jinja2 expressions inside msg to display multiple variables in a single message.

Playbook: debug-multiple.yml

---
- name: Display application details
  hosts: ansible-client
  become: true

  vars:
    application_name: learning-labs
    application_port: 8080
    environment: production

  tasks:
    - name: Display application information
      ansible.builtin.debug:
        msg: |
          Application: {{ application_name }}
          Port: {{ application_port }}
          Environment: {{ environment }}

7. Display Registered Task Results

The Debug module is frequently used with the register keyword to display the output returned by another task.

Playbook: debug-register.yml

---
- name: Display registered command output
  hosts: ansible-client
  become: true

  tasks:
    - name: Get hostname
      ansible.builtin.command:
        cmd: hostname
      register: hostname_result
      changed_when: false

    - name: Display hostname
      ansible.builtin.debug:
        var: hostname_result.stdout

    - name: Display command return code
      ansible.builtin.debug:
        var: hostname_result.rc

The first task captures the command result. The following tasks display its standard output and return code.

8. Display Ansible Facts

Ansible gathers system information from managed hosts as facts. The Debug module can display these facts.

Playbook: debug-facts.yml

---
- name: Display system facts
  hosts: ansible-client
  become: true

  tasks:
    - name: Display operating system
      ansible.builtin.debug:
        var: ansible_distribution

    - name: Display operating system version
      ansible.builtin.debug:
        var: ansible_distribution_version

    - name: Display hostname
      ansible.builtin.debug:
        var: ansible_hostname

    - name: Display total memory
      ansible.builtin.debug:
        var: ansible_memtotal_mb

    - name: Display processor information
      ansible.builtin.debug:
        var: ansible_processor_vcpus

These values depend on the managed host and its environment.

9. Display a Complete Registered Result

You can display the entire registered variable instead of accessing individual fields.

Playbook: debug-full-result.yml

---
- name: Display complete task result
  hosts: ansible-client
  become: true

  tasks:
    - name: Get disk usage
      ansible.builtin.command:
        cmd: df -h /
      register: disk_result
      changed_when: false

    - name: Display complete result
      ansible.builtin.debug:
        var: disk_result

This displays the available fields returned by the task, including standard output, return code and change status.

10. Control Debug Output with Verbosity

The verbosity parameter controls when a Debug task is displayed based on the verbosity level supplied when running the playbook.

Playbook: debug-verbosity.yml

---
- name: Debug verbosity example
  hosts: ansible-client
  become: true

  tasks:
    - name: Always display this message
      ansible.builtin.debug:
        msg: "Normal debug message"

    - name: Display detailed information
      ansible.builtin.debug:
        msg: "Detailed troubleshooting information"
        verbosity: 2

The second task requires Ansible verbosity level 2 or higher.

11. Display Lists and Dictionaries

Debug can display structured data such as lists and dictionaries.

Playbook: debug-structured-data.yml

---
- name: Display structured data
  hosts: ansible-client
  become: true

  vars:
    application:
      name: learning-labs
      port: 8080
      environment: production
      services:
        - frontend
        - backend
        - database

  tasks:
    - name: Display complete application dictionary
      ansible.builtin.debug:
        var: application

    - name: Display application name
      ansible.builtin.debug:
        var: application.name

    - name: Display application services
      ansible.builtin.debug:
        var: application.services

12. Display Values Using Jinja2 Expressions

You can use Jinja2 expressions inside msg to format values and perform simple calculations.

Playbook: debug-jinja.yml

---
- name: Display formatted values
  hosts: ansible-client
  become: true

  vars:
    memory_mb: 4096
    application_port: 8080

  tasks:
    - name: Display memory in GB
      ansible.builtin.debug:
        msg: "Memory: {{ memory_mb / 1024 }} GB"

    - name: Display port information
      ansible.builtin.debug:
        msg: "Application will use port {{ application_port }}"

13. Practical Project: Linux Server Diagnostic Report

Project Objective

Build a playbook that collects Linux system information and displays a readable diagnostic report.

Requirements:
  1. Collect the hostname.
  2. Collect the operating system and version.
  3. Collect the kernel version.
  4. Collect total memory.
  5. Collect root filesystem usage.
  6. Register command output where required.
  7. Display all collected information in a structured report.
Project playbook: linux-diagnostic-report.yml 
---
- name: Generate Linux diagnostic report
  hosts: ansible-client
  become: true

  tasks:
    - name: Collect hostname
      ansible.builtin.command:
        cmd: hostname
      register: hostname_result
      changed_when: false

    - name: Collect kernel version
      ansible.builtin.command:
        cmd: uname -r
      register: kernel_result
      changed_when: false

    - name: Collect root filesystem usage
      ansible.builtin.command:
        cmd: df -h /
      register: disk_result
      changed_when: false

    - name: Display diagnostic report
      ansible.builtin.debug:
        msg:
          - "LINUX SERVER DIAGNOSTIC REPORT"
          - "Hostname: {{ hostname_result.stdout }}"
          - "Operating System: {{ ansible_distribution }}"
          - "OS Version: {{ ansible_distribution_version }}"
          - "Kernel: {{ kernel_result.stdout }}"
          - "Total Memory: {{ ansible_memtotal_mb }} MB"
          - "Root Filesystem:"
          - "{{ disk_result.stdout }}"

14. Important Considerations

  • Debug is primarily used for displaying information during playbook execution.
  • Use msg for custom messages.
  • Use var to display a variable directly.
  • Do not wrap the variable name in Jinja2 braces when using var.
  • Use Jinja2 expressions inside msg when formatting values.
  • Registered results can be inspected using Debug.
  • Facts must be gathered before displaying fact variables.
  • Debug does not modify the managed host.
  • Be careful when displaying passwords, tokens, private keys or other sensitive information.

Why Do We Use the Ansible Debug Module?

In DevOps environments, playbooks often execute many tasks across multiple managed hosts. When something does not behave as expected, engineers need to inspect variables, task results and system information.

The Debug module provides a simple way to display this information during playbook execution. It helps engineers understand the values being processed and identify unexpected results.

For example, after retrieving a server's hostname, disk usage or application configuration, an engineer can use Debug to inspect the returned information before proceeding with additional tasks.

It is commonly used in troubleshooting, automation development, deployment validation and infrastructure diagnostics.
