Ansible Template Module

Learn how to generate dynamic configuration files using Jinja2 templates and deploy them to managed Ubuntu systems.

1. What Is the Template Module?

The ansible.builtin.template module generates configuration files dynamically using Jinja2 templates. It processes variables and expressions on the Ansible controller and deploys the rendered file to the managed host.

For example, suppose you need to configure the same application on multiple Ubuntu servers. Each server requires a different hostname, port, or database address.

Instead of maintaining separate configuration files for every server, you can create one template and supply different values through Ansible variables.

Important: The template source file is stored on the Ansible controller. Ansible renders the template on the controller and transfers the generated configuration file to the target host.

2. Understanding Jinja2 Templates

Jinja2 is a templating language used by Ansible to generate dynamic content.

There are three commonly used Jinja2 syntax types:

Syntax Purpose Example
{{ }} Displays variable values or expressions. {{ app_port }}
{% %} Executes template statements such as loops and conditions. {% if enabled %}
{# #} Adds comments that are not included in the rendered output. {# Application settings #}

3. Understanding the Template Workflow

The template deployment process has four stages:

  1. Create a Jinja2 template on the Ansible controller.
  2. Define variables in the playbook or inventory.
  3. Ansible renders the template using the supplied variables.
  4. The generated file is deployed to ansible-client.

4. Basic Template Example

First, create a directory named templates inside your Ansible project on the controller. 

ansible-project/
├── application.yml
└── templates/
    └── app.conf.j2

Step 1: Create the Template File

Create templates/app.conf.j2:

APP_NAME={{ app_name }}
APP_PORT={{ app_port }}
APP_ENV={{ app_environment }}

Step 2: Create the Playbook

Create application.yml:

---
- name: Deploy application configuration
  hosts: ansible-client
  become: true

  vars:
    app_name: learning-labs
    app_port: 8080
    app_environment: production

  tasks:
    - name: Create configuration directory
      ansible.builtin.file:
        path: /tmp/ansible-template-lab
        state: directory
        mode: '0755'

    - name: Deploy application configuration
      ansible.builtin.template:
        src: templates/app.conf.j2
        dest: /tmp/ansible-template-lab/app.conf
        mode: '0644'

Step 3: Expected Output

Ansible replaces the Jinja2 variables with their values and creates the following file on ansible-client: 

APP_NAME=learning-labs
APP_PORT=8080
APP_ENV=production

5. Important Template Module Parameters

Parameter Description
src Path to the Jinja2 template on the controller.
dest Destination path on the managed host.
owner Sets the owner of the generated file.
group Sets the group ownership of the generated file.
mode Sets file permissions.
backup Creates a backup before replacing an existing destination file.
force Controls whether the destination file is replaced when it already exists. Default is true.
validate Validates the rendered temporary file before replacing the destination.
newline_sequence Controls the newline character sequence in the rendered file.
variable_start_string Changes the default Jinja2 variable opening delimiter.
variable_end_string Changes the default Jinja2 variable closing delimiter.
trim_blocks Controls removal of the first newline after a Jinja2 block.
lstrip_blocks Removes leading spaces and tabs before Jinja2 block tags.

6. Using Variables in Templates

Variables allow you to reuse the same template with different configuration values.

Template: templates/server.conf.j2

SERVER_NAME={{ server_name }}
SERVER_IP={{ server_ip }}
SERVER_PORT={{ server_port }}
ENVIRONMENT={{ environment }}

Playbook:

---
- name: Configure server settings
  hosts: ansible-client
  become: true

  vars:
    server_name: app-server
    server_ip: 192.168.1.20
    server_port: 8080
    environment: production

  tasks:
    - name: Deploy server configuration
      ansible.builtin.template:
        src: templates/server.conf.j2
        dest: /tmp/ansible-template-lab/server.conf
        mode: '0644'

Generated file:

SERVER_NAME=app-server
SERVER_IP=192.168.1.20
SERVER_PORT=8080
ENVIRONMENT=production

7. Using Conditional Statements

Jinja2 supports conditional statements. You can generate different configuration content depending on variable values.

Template: templates/app.conf.j2

APP_NAME={{ app_name }}
APP_PORT={{ app_port }}

{% if environment == "production" %}
APP_DEBUG=false
LOG_LEVEL=WARNING
{% else %}
APP_DEBUG=true
LOG_LEVEL=DEBUG
{% endif %}

Playbook:

---
- name: Generate environment-specific configuration
  hosts: ansible-client
  become: true

  vars:
    app_name: learning-labs
    app_port: 8080
    environment: production

  tasks:
    - name: Deploy configuration
      ansible.builtin.template:
        src: templates/app.conf.j2
        dest: /tmp/ansible-template-lab/app.conf
        mode: '0644'

When the environment is production, the generated file contains production-specific settings.

8. Using Loops Inside Templates

Jinja2 supports loops. You can generate repeated configuration entries from a list of variables.

Template: templates/servers.conf.j2

{% for server in servers %}
SERVER={{ server.name }}
IP={{ server.ip }}
PORT={{ server.port }}

{% endfor %}

Playbook:

---
- name: Generate server configuration
  hosts: ansible-client
  become: true

  vars:
    servers:
      - name: web01
        ip: 192.168.1.10
        port: 8080

      - name: web02
        ip: 192.168.1.11
        port: 8081

      - name: web03
        ip: 192.168.1.12
        port: 8082

  tasks:
    - name: Deploy server list
      ansible.builtin.template:
        src: templates/servers.conf.j2
        dest: /tmp/ansible-template-lab/servers.conf
        mode: '0644'

Generated file:

SERVER=web01
IP=192.168.1.10
PORT=8080

SERVER=web02
IP=192.168.1.11
PORT=8081

SERVER=web03
IP=192.168.1.12
PORT=8082

9. Using Ansible Facts in Templates

Ansible facts provide information collected from managed hosts. These facts can be referenced directly inside Jinja2 templates.

Template: templates/system-info.conf.j2

HOSTNAME={{ ansible_hostname }}
OPERATING_SYSTEM={{ ansible_distribution }}
OS_VERSION={{ ansible_distribution_version }}
ARCHITECTURE={{ ansible_architecture }}
IP_ADDRESS={{ ansible_default_ipv4.address }}

Playbook:

---
- name: Generate system information
  hosts: ansible-client
  become: true
  gather_facts: true

  tasks:
    - name: Deploy system information
      ansible.builtin.template:
        src: templates/system-info.conf.j2
        dest: /tmp/ansible-template-lab/system-info.conf
        mode: '0644'
Note: The facts shown above depend on the target system and available network configuration. The default IPv4 address fact may not exist on a host without a suitable default network interface.

10. Creating Backups Before Replacing Files

Use backup: true when you want to preserve the previous destination file before deploying a new rendered file. 

---
- name: Deploy configuration with backup
  hosts: ansible-client
  become: true

  tasks:
    - name: Deploy updated application configuration
      ansible.builtin.template:
        src: templates/app.conf.j2
        dest: /tmp/ansible-template-lab/app.conf
        backup: true
        mode: '0644'

11. Validating a Rendered Template

The validate parameter checks the rendered temporary file before Ansible replaces the destination file. 

---
- name: Validate generated configuration
  hosts: ansible-client
  become: true

  tasks:
    - name: Deploy validated configuration
      ansible.builtin.template:
        src: templates/app.conf.j2
        dest: /tmp/ansible-template-lab/app.conf
        validate: '/usr/bin/test -s %s'
        mode: '0644'

This example checks that the rendered file is not empty. In production, use the application's actual configuration validation command where available.

12. Understanding Idempotency

The template module is idempotent. It compares the rendered content with the destination file and updates the file when the content differs.

  • First execution: The destination file is created.
  • Second execution: No change occurs if the rendered content is identical.
  • Variable change: The template is rendered again and the destination is updated if necessary.
Important: Avoid using timestamps or other changing values in templates unless you intend to update the destination on every run.

13. Practical Project: Dynamic Application Configuration

In this project, you will create a reusable Jinja2 template and deploy an application configuration file to ansible-client.

Project Requirements

  • Create a Jinja2 template on the controller.
  • Use variables for application settings.
  • Use conditions for production and development environments.
  • Generate multiple server entries using a loop.
  • Include system information from Ansible facts.
  • Deploy the rendered configuration to ansible-client.
  • Create a backup before replacing the destination file.

Step 1: Create the Project Structure

ansible-template-project/
├── application.yml
└── templates/
    └── application.conf.j2

Step 2: Create the Jinja2 Template

Create templates/application.conf.j2:

# Application Configuration

APP_NAME={{ app_name }}
APP_PORT={{ app_port }}
APP_ENVIRONMENT={{ app_environment }}

{% if app_environment == "production" %}
APP_DEBUG=false
LOG_LEVEL=WARNING
{% else %}
APP_DEBUG=true
LOG_LEVEL=DEBUG
{% endif %}

# Backend Servers

{% for server in backend_servers %}
SERVER_NAME={{ server.name }}
SERVER_IP={{ server.ip }}
SERVER_PORT={{ server.port }}

{% endfor %}

# Managed Host Information

HOSTNAME={{ ansible_hostname }}
OS={{ ansible_distribution }}
OS_VERSION={{ ansible_distribution_version }}

Step 3: Create the Playbook

Create application.yml:

---
- name: Deploy dynamic application configuration
  hosts: ansible-client
  become: true
  gather_facts: true

  vars:
    app_name: learning-labs
    app_port: 8080
    app_environment: production

    backend_servers:
      - name: backend01
        ip: 192.168.1.10
        port: 8081

      - name: backend02
        ip: 192.168.1.11
        port: 8082

      - name: backend03
        ip: 192.168.1.12
        port: 8083

  tasks:

    - name: Create application configuration directory
      ansible.builtin.file:
        path: /tmp/ansible-template-project
        state: directory
        mode: '0755'

    - name: Deploy application configuration
      ansible.builtin.template:
        src: templates/application.conf.j2
        dest: /tmp/ansible-template-project/application.conf
        owner: root
        group: root
        mode: '0644'
        backup: true

    - name: Display deployment result
      ansible.builtin.debug:
        msg: "Application configuration deployed successfully."

Step 4: Expected Output

The generated file on ansible-client will contain the rendered application settings, backend server entries, and target system information. 

# Application Configuration

APP_NAME=learning-labs
APP_PORT=8080
APP_ENVIRONMENT=production

APP_DEBUG=false
LOG_LEVEL=WARNING

# Backend Servers

SERVER_NAME=backend01
SERVER_IP=192.168.1.10
SERVER_PORT=8081

SERVER_NAME=backend02
SERVER_IP=192.168.1.11
SERVER_PORT=8082

SERVER_NAME=backend03
SERVER_IP=192.168.1.12
SERVER_PORT=8083

# Managed Host Information

HOSTNAME=ansible-client
OS=Ubuntu
OS_VERSION=24.04

The actual hostname and operating system values depend on the target Ubuntu environment.

Step 5: Verify the Generated File

Create verify-application.yml:

---
- name: Verify generated application configuration
  hosts: ansible-client
  become: true

  tasks:
    - name: Read generated configuration
      ansible.builtin.slurp:
        src: /tmp/ansible-template-project/application.conf
      register: generated_config

    - name: Display generated configuration
      ansible.builtin.debug:
        msg: "{{ generated_config.content | b64decode }}"

Step 6: Test Idempotency

Execute the deployment playbook again without changing the template or variables. The template task should report no change when the rendered content is identical.

Project outcome: You have created a reusable Jinja2 template that generates dynamic application configuration and deploys it to the ansible-client Ubuntu host.

Why Do We Use the Ansible Template Module?

In infrastructure environments, applications often require configuration files containing values that differ between development, testing, staging, and production systems. Maintaining separate static configuration files for every environment creates duplication and increases maintenance effort.

The Ansible template module solves this problem by allowing administrators to maintain one reusable Jinja2 template. Variables, conditions, loops, and Ansible facts can be used to generate different configuration files for different managed systems.

The template is processed on the Ansible controller. The generated content is then deployed to the destination path on the managed host.

Practical Reasons to Use It

  • Reusable configuration: Maintain one template instead of separate static configuration files for every environment.
  • Dynamic values: Generate configuration files using variables from playbooks, inventories, and host facts.
  • Environment-specific configuration: Generate different settings for development, testing, and production.
  • Automated application deployment: Generate application configuration files as part of deployment workflows.
  • Reduced duplication: Reuse the same template across multiple managed hosts.
  • Consistent configuration: Standardize configuration generation across an infrastructure environment.
  • Idempotent management: Update destination files only when the rendered content differs.

Real-World DevOps Example

Imagine an organization deploying an application across development, staging, and production environments. Each environment has a different database address, application port, and logging configuration.

Instead of maintaining three separate configuration files, the DevOps engineer creates one Jinja2 template and supplies the environment-specific values through Ansible variables.

Ansible renders the appropriate configuration for each managed host and deploys the generated file.

This makes the template module particularly useful for application deployment, configuration management, and infrastructure automation.

Remember: Use template when you need to generate a complete file dynamically. Use copy for static files, lineinfile for individual lines, blockinfile for multiline sections, and replace for pattern-based text replacement.
