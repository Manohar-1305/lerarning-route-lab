Ansible changed_when Keyword

The Ansible changed_when keyword controls whether Ansible reports a task as changed or unchanged. It allows engineers to define custom conditions for determining the change status of a task.

1. What Is changed_when?

Ansible modules normally report whether a task changed something. However, certain modules such as Command and Shell cannot always determine whether the command actually changed the system.

The changed_when keyword allows you to define your own logic for reporting the task status.

Common use cases include:

  • Preventing read-only commands from reporting changes.
  • Reporting a change only when command output meets a condition.
  • Determining change status using a registered return code.
  • Controlling change reporting for custom scripts.
  • Making Ansible playbook output more accurate.
  • Controlling whether a task is considered changed for reporting and handlers.

2. Understanding Ansible Task Status

Ansible commonly reports the following task statuses:

Status Meaning
ok The task completed without reporting a change.
changed The task reports that something changed.
failed The task failed.
skipped The task was not executed because its condition was not met.

3. How Does changed_when Work?

             Ansible Controller
             ------------------
                    |
                    v
                Playbook
                    |
                    v
                Execute Task
                    |
                    v
             Evaluate changed_when
                    |
             +------+------+
             |             |
           TRUE          FALSE
             |             |
             v             v
        Report Changed   Report OK
                    |
                    v
             Continue Playbook

Ansible evaluates the expression configured under changed_when.

  • If the expression is true, the task reports changed.
  • If the expression is false, the task reports ok.
Important: changed_when controls Ansible's reported change status. It does not prevent a command from modifying the system or make a non-idempotent command idempotent.

4. Basic changed_when Syntax

The keyword is written at the task level, alongside the module. 

---
- name: Basic changed_when example
  hosts: ansible-client
  become: true

  tasks:
    - name: Execute a command
      ansible.builtin.command:
        cmd: hostname
      changed_when: false

The hostname command executes, but Ansible reports the task as unchanged because the condition is explicitly set to false.

5. Use changed_when: false

Use changed_when: false for read-only commands that do not modify the managed host.

Playbook: changed-when-false.yml

---
- name: Execute read-only commands
  hosts: ansible-client
  become: true

  tasks:
    - name: Get hostname
      ansible.builtin.command:
        cmd: hostname
      changed_when: false

    - name: Get kernel version
      ansible.builtin.command:
        cmd: uname -r
      changed_when: false

    - name: Get disk usage
      ansible.builtin.command:
        cmd: df -h /
      changed_when: false

    - name: Get current date
      ansible.builtin.command:
        cmd: date
      changed_when: false

These commands retrieve information without intentionally changing the system. The playbook reports them as unchanged.

6. Use changed_when: true

You can explicitly make a task report a change by setting changed_when: true.

Playbook: changed-when-true.yml

---
- name: Force changed status
  hosts: ansible-client
  become: true

  tasks:
    - name: Execute hostname command
      ansible.builtin.command:
        cmd: hostname
      changed_when: true

Even though the hostname command does not modify the system, Ansible reports this task as changed.

Important: This example demonstrates change-status reporting only. Do not use changed_when: true indiscriminately for read-only tasks.

7. Use changed_when with Register

You can combine register and changed_when to determine task status based on the result returned by a command.

Playbook: changed-when-register.yml

---
- name: Determine change status from command output
  hosts: ansible-client
  become: true

  tasks:
    - name: Check application directory
      ansible.builtin.command:
        cmd: test -d /tmp/learning-labs
      register: directory_result
      changed_when: false
      failed_when: false

    - name: Display directory status
      ansible.builtin.debug:
        msg: "Directory check return code: {{ directory_result.rc }}"

The directory check is read-only. It is always reported as unchanged, regardless of whether the directory exists.

8. Determine Change Status Using stdout

You can evaluate command output and report a change only when the output contains a particular value.

Playbook: changed-when-stdout.yml

---
- name: Determine change status using output
  hosts: ansible-client
  become: true

  tasks:
    - name: Generate a command result
      ansible.builtin.command:
        cmd: echo "CONFIGURATION_UPDATED"
      register: command_result
      changed_when: "'CONFIGURATION_UPDATED' in command_result.stdout"

If the command output contains CONFIGURATION_UPDATED, Ansible reports the task as changed.

Important: The example demonstrates how output controls the reported status. The echo command itself does not modify the system.

9. Determine Change Status Using Return Code

You can use the registered command return code to determine whether Ansible should report a change.

Playbook: changed-when-rc.yml

---
- name: Determine status using return code
  hosts: ansible-client
  become: true

  tasks:
    - name: Check whether application directory exists
      ansible.builtin.command:
        cmd: test -d /tmp/learning-labs
      register: directory_result
      changed_when: directory_result.rc == 0
      failed_when: false

The task reports changed when the directory exists and unchanged when it does not.

This example only demonstrates custom status reporting. It does not create or modify the directory.

10. Use Multiple Conditions

You can define multiple expressions under changed_when. All expressions must be true for the task to report changed.

Playbook: changed-when-multiple.yml

---
- name: Evaluate multiple change conditions
  hosts: ansible-client
  become: true

  tasks:
    - name: Generate application status
      ansible.builtin.command:
        cmd: echo "APP_UPDATED"
      register: application_result
      changed_when:
        - "'APP_UPDATED' in application_result.stdout"
        - application_result.rc == 0

Both conditions must be true for Ansible to report the task as changed.

11. Use changed_when with Shell

The keyword also works with the Shell module.

Playbook: changed-when-shell.yml

---
- name: Control Shell task status
  hosts: ansible-client
  become: true

  tasks:
    - name: Count running processes
      ansible.builtin.shell:
        cmd: ps aux | wc -l
      register: process_result
      changed_when: false

    - name: Display process count
      ansible.builtin.debug:
        msg: "Process count: {{ process_result.stdout }}"

The command collects information without intentionally changing the system. Therefore, the task is reported as unchanged.

12. Understanding changed_when and Idempotency

Idempotency means that running the same automation repeatedly produces the same desired system state without unnecessary changes.

The changed_when keyword does not itself provide idempotency. It only controls how Ansible reports the result.

Example: A command that creates a file

---
- name: Create report file
  hosts: ansible-client
  become: true

  tasks:
    - name: Create report if it does not exist
      ansible.builtin.command:
        cmd: touch /tmp/ansible-report.txt
        creates: /tmp/ansible-report.txt

The Command module's creates parameter skips the command when the file already exists. This prevents unnecessary execution on subsequent runs.

The command module can therefore report changed on the first run and unchanged on later runs.

13. Practical Project: Linux System Information Collector

Project Objective

Build a playbook that collects Linux system information while accurately reporting read-only tasks as unchanged.

Requirements:
  1. Collect the hostname.
  2. Collect the kernel version.
  3. Collect memory information.
  4. Collect root filesystem usage.
  5. Use Register to capture command results.
  6. Use changed_when to report read-only tasks as unchanged.
  7. Display the collected information.
Project playbook: system-information.yml 
---
- name: Collect Linux system information
  hosts: ansible-client
  become: true

  tasks:
    - name: Collect hostname
      ansible.builtin.command:
        cmd: hostname
      register: hostname_result
      changed_when: false

    - name: Collect kernel version
      ansible.builtin.command:
        cmd: uname -r
      register: kernel_result
      changed_when: false

    - name: Collect memory information
      ansible.builtin.command:
        cmd: free -h
      register: memory_result
      changed_when: false

    - name: Collect root filesystem usage
      ansible.builtin.command:
        cmd: df -h /
      register: disk_result
      changed_when: false

    - name: Display system information
      ansible.builtin.debug:
        msg:
          - "Hostname: {{ hostname_result.stdout }}"
          - "Kernel: {{ kernel_result.stdout }}"
          - "Memory information:"
          - "{{ memory_result.stdout }}"
          - "Root filesystem:"
          - "{{ disk_result.stdout }}"

14. Important Considerations

  • changed_when is a playbook keyword, not a module.
  • It controls Ansible's reported change status.
  • It does not prevent commands from modifying the managed host.
  • Use changed_when: false for appropriate read-only commands.
  • Use expressions when change status depends on command output.
  • Registered variables can be used inside change conditions.
  • Multiple conditions in a YAML list must all evaluate to true.
  • Do not confuse change reporting with idempotency.
  • Incorrect change reporting can affect handlers and playbook statistics.

Why Do We Use the Ansible changed_when Keyword?

In production automation, accurate task reporting is important. Engineers need to distinguish between tasks that actually modify a system and tasks that simply collect information.

For example, commands such as hostname, uname and df retrieve information. They do not intentionally modify the managed host. However, command-based tasks may otherwise report a change.

The changed_when keyword allows engineers to define how Ansible should report these tasks. This improves playbook output and makes change reporting more meaningful.

It is commonly used with Command, Shell and custom automation tasks where the default change detection does not accurately represent the operation.
