Ansible Group Module

In this lab, you will learn how to manage Linux groups using the Ansible Group module. You will create groups, assign specific group IDs, create system groups and remove groups through Ansible playbooks.

At the end, you will build a practical project that automates Linux group management for different application teams.

1. What Is the Group Module?

Linux uses groups to organize user accounts and manage access to files, directories and other system resources.

Every Linux user has a primary group and can also belong to additional supplementary groups.

Instead of assigning permissions individually to multiple users, administrators can assign users to a group and manage permissions for that group.

Ansible provides the ansible.builtin.group module to create, modify and remove Linux groups.

The fully qualified module name is: 

ansible.builtin.group

2. Understanding Linux Groups

Consider an organization with three teams:

  • Developers who work on application source code.
  • Administrators who manage server operations.
  • Testers who access testing-related files.

Instead of managing access for every user individually, an administrator can create three Linux groups: 

developers
administrators
testers

Users can then be assigned to the appropriate groups. File and directory permissions can be configured using group ownership.

For example, a directory owned by the developers group can be configured to allow members of that group to access its contents according to the assigned permissions.

3. Group Module Syntax

The basic structure of the Group module looks like this: 

- name: Create a Linux group
  ansible.builtin.group:
    name: developers
    state: present

ansible.builtin.group identifies the module. The name parameter specifies the group, and state defines whether the group should exist or be absent.

4. Important Group Module Parameters

name

Specifies the name of the Linux group that Ansible should manage. 

name: developers

In this example, Ansible manages a group named developers.

state

Specifies the desired state of the group.

  • present – Ensures that the group exists.
  • absent – Ensures that the group is removed.

When state: present is used, Ansible creates the group if it does not already exist.

If the group already exists, Ansible checks whether the requested attributes need to be changed.

gid

Specifies the numeric Group ID assigned to the Linux group. 

gid: 2001

Every Linux group has a numeric GID. The operating system uses this identifier internally to represent group ownership.

In this example, Ansible requests GID 2001 for the group.

The requested GID must not already be assigned to another group. Otherwise, group creation can fail.

system

Specifies whether the group should be created as a system group. 

system: true

A system group is generally used for operating system services and applications rather than regular users.

The operating system selects a GID from its configured system group range when one is not explicitly provided.

This is useful when creating groups for application services that require dedicated group identities.

force

Controls whether a group can be forcibly removed. 

state: absent
force: true

This parameter is relevant when deleting a group. It requests forced removal where supported by the underlying system tools.

Use forced group deletion carefully. Check whether users or files still depend on the group before removing it.

5. Create a Single Group

Create a playbook named create-group.yml. In this example, you will create a group named developers. 

---
- name: Create Linux Group
  hosts: localhost
  connection: local
  become: true

  tasks:
    - name: Create developers group
      ansible.builtin.group:
        name: developers
        state: present

Understanding the Playbook

hosts: localhost targets the local Ubuntu system.

connection: local tells Ansible to execute the tasks locally.

become: true enables administrative privileges because creating Linux groups requires elevated permissions.

name: developers specifies the group to create.

state: present ensures that the developers group exists.

6. Create a Group with a Specific GID

You can assign a specific numeric Group ID when creating a Linux group.

Create create-group-gid.yml. 

---
- name: Create Group with Specific GID
  hosts: localhost
  connection: local
  become: true

  tasks:
    - name: Create application group
      ansible.builtin.group:
        name: appgroup
        gid: 2001
        state: present

Understanding the Playbook

name: appgroup specifies the Linux group name.

gid: 2001 requests Group ID 2001.

state: present ensures that the group exists.

Assigning a consistent GID can be useful when group ownership needs to be consistent across multiple servers.

Before assigning a fixed GID, verify that it is available on every target system.

7. Create Multiple Groups

Ansible allows you to create multiple groups using a loop. This is useful when configuring different teams or applications.

Create create-multiple-groups.yml. 

---
- name: Create Multiple Linux Groups
  hosts: localhost
  connection: local
  become: true

  tasks:
    - name: Create team groups
      ansible.builtin.group:
        name: "{{ item }}"
        state: present
      loop:
        - developers
        - testers
        - administrators
        - monitoring

Understanding the Playbook

loop allows the same task to execute for each value in the list.

item represents the current group name being processed.

Ansible creates the following four groups:

  • developers
  • testers
  • administrators
  • monitoring

The same task is reused for every group instead of writing four separate tasks.

8. Create a System Group

Applications and services sometimes require dedicated Linux groups. You can create these using the system parameter.

Create create-system-group.yml. 

---
- name: Create Application System Group
  hosts: localhost
  connection: local
  become: true

  tasks:
    - name: Create application system group
      ansible.builtin.group:
        name: appservice
        system: true
        state: present

Understanding the Playbook

name: appservice specifies the group name.

system: true requests a system group.

state: present ensures that the group exists.

System groups are commonly used to organize application service accounts and assign group ownership to application resources.

9. Remove a Group

The Group module can also remove an existing Linux group.

Create remove-group.yml. 

---
- name: Remove Linux Group
  hosts: localhost
  connection: local
  become: true

  tasks:
    - name: Remove testers group
      ansible.builtin.group:
        name: testers
        state: absent

Understanding the Playbook

name: testers identifies the group to remove.

state: absent requests removal of the group.

The group should not have dependent users or resources that still require its ownership and membership.

Removing a group does not automatically delete the user accounts that belong to it. Check group dependencies and file ownership before removing an existing group.

10. Verify Linux Groups

After executing a playbook, you can inspect the group information to confirm that the group was created.

Check a Specific Group

getent group developers

This displays the group entry, including its name, password field, GID and listed supplementary members.

Display All Groups

getent group

This displays the group entries available through the system's configured group databases.

Check a Group's GID

getent group appgroup

The output includes the numeric GID assigned to appgroup.

Check a User's Group Membership

id devops

This displays the user's UID, primary GID and supplementary group memberships.

11. Practical Project: Linux Team Group Management

In this project, you will automate Linux group management for different teams in an organization.

The organization has developers, testers, administrators and monitoring teams. Each team requires a dedicated Linux group.

You will create all the groups through one Ansible playbook and assign specific GIDs to selected groups.

Project Requirements

  • Create a developers group with GID 2101.
  • Create a testers group with GID 2102.
  • Create an administrators group with GID 2103.
  • Create a monitoring group with GID 2104.
  • Create an application system group named appservice.
  • Ensure all requested groups exist.
  • Verify the group names and GIDs after execution.

Step 1: Create the Project Directory

mkdir -p linux-group-management
cd linux-group-management

Step 2: Create the Main Playbook

Create a file named group-management.yml. 

---
- name: Linux Team Group Management
  hosts: localhost
  connection: local
  become: true

  tasks:

    - name: Create developers group
      ansible.builtin.group:
        name: developers
        gid: 2101
        state: present

    - name: Create testers group
      ansible.builtin.group:
        name: testers
        gid: 2102
        state: present

    - name: Create administrators group
      ansible.builtin.group:
        name: administrators
        gid: 2103
        state: present

    - name: Create monitoring group
      ansible.builtin.group:
        name: monitoring
        gid: 2104
        state: present

    - name: Create application system group
      ansible.builtin.group:
        name: appservice
        system: true
        state: present

Step 3: Understand the Project Playbook

The playbook contains five tasks.

The first four tasks create regular Linux groups for developers, testers, administrators and monitoring.

Each group receives a specific GID so that its numeric identity is explicitly defined.

The fifth task creates an application system group using system: true.

All tasks use state: present, ensuring that the requested groups exist.

Step 4: Validate the Playbook

Validate the YAML syntax and playbook structure. 

ansible-playbook group-management.yml --syntax-check

Step 5: Execute the Playbook

ansible-playbook group-management.yml

Ansible executes each task and creates the required Linux groups.

Step 6: Verify the Created Groups

getent group developers
getent group testers
getent group administrators
getent group monitoring
getent group appservice

Step 7: Execute the Playbook Again

Run the same playbook again: 

ansible-playbook group-management.yml

Since the requested groups already exist with the expected configuration, Ansible should report ok for tasks that do not require changes.

Project completed: You have automated Linux team group management using the Ansible Group module.

Why Do We Use the Ansible Group Module?

Linux groups provide a way to organize user accounts and manage access to shared resources. Instead of assigning permissions individually to every user, administrators can organize users into groups and manage permissions at the group level.

In organizations with multiple Linux servers, group management can become repetitive. Administrators may need to create the same groups, assign specific GIDs and maintain consistent group configurations across different systems.

The Ansible Group module automates these operations through playbooks.

1. Centralized Group Management

Consider an organization with 50 Ubuntu servers. Every server requires developers, testers and administrators groups.

Without automation, an administrator would need to create these groups manually on every server.

With the Ansible Group module, the administrator can define the required groups in one playbook and apply the configuration to all selected servers.

This reduces repetitive manual work and simplifies group administration.

2. Consistent Group IDs Across Servers

Every Linux group has a numeric Group ID. The operating system uses this GID to identify group ownership of files and directories.

When multiple servers share files or storage, inconsistent GIDs can cause ownership and access problems.

For example, the developers group may use GID 2101 on one server but GID 2201 on another server.

Explicitly managing GIDs helps maintain consistent group identities across systems where shared ownership is required.

3. Simplified Permission Management

Linux file permissions can be assigned to the owner, group and other users.

By creating groups, administrators can manage access for multiple users through a common group identity.

For example, developers can belong to the developers group, and a shared project directory can be assigned to that group.

This allows permissions to be managed at the group level rather than individually for every developer.

4. Team-Based Access Organization

Different teams have different responsibilities. Developers may need access to application source files, testers may need access to testing resources, and administrators may need access to operational resources.

The Group module helps create and maintain these team-specific groups.

When combined with the User module, Ansible can create user accounts and assign them to the appropriate groups.

5. Application Service Groups

Applications and services may require dedicated Linux groups to manage access to application files and resources.

A system group can provide a separate group identity for an application service.

The system: true parameter allows Ansible to request the creation of a system group.

This helps separate application-related identities from regular user groups.

6. Automated Group Removal

Groups that are no longer required may need to be removed as part of infrastructure maintenance.

The Group module supports group removal through state: absent.

Before deleting a group, administrators should verify whether users or files still depend on it.

7. Idempotency and Repeatable Automation

Ansible checks whether the requested group already exists before creating it.

If the group exists with the requested configuration, Ansible does not need to recreate it.

If the group is missing, Ansible creates it.

This makes group management repeatable and reduces unnecessary changes during repeated playbook executions.

8. Why Is This Important for a DevOps Engineer?

DevOps engineers frequently manage application servers, development environments, shared directories and service accounts.

These environments require consistent user and group configurations to control access to system resources.

Understanding the Group module helps automate group creation, maintain consistent GIDs and organize team-based access across Linux infrastructure.

When combined with the User, File and Copy modules, it becomes possible to automate a complete Linux access and directory configuration workflow.
