Ansible Roles

Ansible Roles provide a standardized directory structure for organizing automation content. They allow you to separate tasks, variables, files, templates, and handlers into reusable components.

1. Why Do We Need Ansible Roles?

Consider a production environment where you need to configure multiple servers:

  • Web servers require Nginx installation and configuration.
  • Database servers require database packages and configuration.
  • Application servers require application dependencies and deployment.

Writing all these tasks in one large playbook makes automation difficult to maintain.

Roles allow you to organize each responsibility separately and reuse it across multiple playbooks.

2. What Is an Ansible Role?

An Ansible Role is a collection of related automation files organized in a predefined directory structure.

A typical role looks like this:

roles/
└── webserver/
    ├── defaults/
    │   └── main.yml
    ├── files/
    ├── handlers/
    │   └── main.yml
    ├── meta/
    │   └── main.yml
    ├── tasks/
    │   └── main.yml
    ├── templates/
    ├── tests/
    └── vars/
        └── main.yml

3. Understanding the Role Directory Structure

Directory Purpose
tasks/ Contains the main tasks executed by the role.
handlers/ Contains handlers triggered by notifications.
defaults/ Contains default variables with the lowest variable precedence.
vars/ Contains role variables with higher precedence than defaults.
files/ Contains static files copied to managed hosts.
templates/ Contains Jinja2 templates processed by Ansible.
meta/ Contains role metadata, including role dependencies.
tests/ Can contain test playbooks and inventory files.

4. Create an Ansible Role

Ansible provides the ansible-galaxy command to create a role directory structure.

Run this command on your Ansible controller:

ansible-galaxy role init webserver

This creates a role named webserver with the standard directories and files.

For this lab, use the following project structure:

ansible-project/
├── inventory
├── main.yml
└── roles/
    └── webserver/
        ├── defaults/
        │   └── main.yml
        ├── handlers/
        │   └── main.yml
        ├── tasks/
        │   └── main.yml
        └── templates/

5. Define Tasks Inside a Role

Open roles/webserver/tasks/main.yml.

---
- name: Create web application directory
  ansible.builtin.file:
    path: /opt/webserver
    state: directory
    mode: '0755'

- name: Create web application configuration
  ansible.builtin.copy:
    dest: /opt/webserver/index.html
    content: |
      Welcome to the Ansible Role Lab
    mode: '0644'

This file contains the tasks that the role executes.

6. Define Default Variables

Open roles/webserver/defaults/main.yml.

---
webserver_root: /opt/webserver
webserver_page_title: "Ansible Role Lab"
webserver_page_content: "Welcome to the webserver role"

Default variables make the role configurable without modifying its task definitions.

7. Use Variables Inside Role Tasks

Update roles/webserver/tasks/main.yml to use the default variables.

---
- name: Create webserver directory
  ansible.builtin.file:
    path: "{{ webserver_root }}"
    state: directory
    mode: '0755'

- name: Create webserver page
  ansible.builtin.copy:
    dest: "{{ webserver_root }}/index.html"
    content: |
      {{ webserver_page_title }}
      {{ webserver_page_content }}
    mode: '0644'

The role now uses variables instead of hardcoded directory and content values.

8. Execute a Role from a Playbook

Create a main playbook named main.yml.

---
- name: Configure webserver
  hosts: ansible-client
  become: true

  roles:
    - webserver

Ansible automatically discovers the role when it is available in the project's roles/ directory.

Execute the playbook:

ansible-playbook main.yml
Important: The role name in the playbook must match the role directory name. In this example, the directory is roles/webserver/, so the role is referenced as webserver.

9. Use a Role with a Different Variable Value

You can override the role's default variables from the playbook.

---
- name: Configure custom webserver
  hosts: ansible-client
  become: true

  roles:
    - role: webserver
      vars:
        webserver_root: /opt/custom-webserver
        webserver_page_title: "Custom Webserver"
        webserver_page_content: "Configured using role variables"

The role uses these supplied values instead of its defaults.

10. Execute Multiple Roles

A playbook can execute multiple roles in sequence.

Example directory structure:

roles/
├── webserver/
│   └── tasks/
│       └── main.yml
├── application/
│   └── tasks/
│       └── main.yml
└── monitoring/
    └── tasks/
        └── main.yml

main.yml

---
- name: Configure application server
  hosts: ansible-client
  become: true

  roles:
    - webserver
    - application
    - monitoring

Ansible executes the roles in the order listed in the playbook.

11. Practical Project: Build a Reusable Application Role

Objective

Create a reusable role that prepares an application directory and generates a configuration file on the Ubuntu client.

Project structure:

application-project/
├── main.yml
└── roles/
    └── application/
        ├── defaults/
        │   └── main.yml
        └── tasks/
            └── main.yml

Step 1: Create the role

ansible-galaxy role init application

Step 2: Configure defaults/main.yml

---
app_name: LearningLabs
app_directory: /opt/learninglabs
app_environment: development

Step 3: Configure tasks/main.yml

---
- name: Create application directory
  ansible.builtin.file:
    path: "{{ app_directory }}"
    state: directory
    mode: '0755'

- name: Create application configuration
  ansible.builtin.copy:
    dest: "{{ app_directory }}/application.conf"
    content: |
      APP_NAME={{ app_name }}
      APP_ENV={{ app_environment }}
    mode: '0644'

- name: Create application log directory
  ansible.builtin.file:
    path: "{{ app_directory }}/logs"
    state: directory
    mode: '0755'

Step 4: Create main.yml

---
- name: Deploy LearningLabs application structure
  hosts: ansible-client
  become: true

  roles:
    - application

Step 5: Execute the role

ansible-playbook main.yml

Step 6: Verify using a playbook

Create verify.yml:

---
- name: Verify application role
  hosts: ansible-client
  become: true

  tasks:
    - name: Read application configuration
      ansible.builtin.command: cat /opt/learninglabs/application.conf
      register: app_config
      changed_when: false

    - name: Display application configuration
      ansible.builtin.debug:
        var: app_config.stdout

    - name: Check application log directory
      ansible.builtin.command: test -d /opt/learninglabs/logs
      changed_when: false

Execute:

ansible-playbook verify.yml

Expected Result

The Ubuntu client should contain:

/opt/learninglabs/
├── application.conf
└── logs/

The configuration file should contain:

APP_NAME=LearningLabs
APP_ENV=development

12. Important Points

  • A role is a reusable collection of related Ansible content.
  • The tasks/main.yml file is the role's default task entry point.
  • The defaults/main.yml file defines default variables.
  • Roles can be reused across multiple playbooks.
  • Multiple roles can be executed in a single play.
  • Roles can contain tasks, handlers, variables, files, templates, and metadata.

Why Do We Use Ansible Roles?

We use Ansible Roles to organize automation into reusable and maintainable components.

In enterprise DevOps environments, different teams may maintain automation for web servers, databases, monitoring, security, and application deployments.

Roles allow each responsibility to be maintained independently. A webserver role can be reused across multiple environments without copying the same tasks into every playbook.

For example, you can maintain separate roles for Nginx configuration, application deployment, user management, and monitoring configuration.

This makes automation easier to scale, maintain, test, and share across projects.
