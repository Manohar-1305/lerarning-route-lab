Ansible failed_when Keyword

The failed_when keyword allows you to define your own conditions for deciding whether an Ansible task should be marked as failed.

1. What Is failed_when?

By default, Ansible considers a task failed when the executed module reports a failure. For command and shell tasks, a non-zero return code normally indicates failure.

The failed_when keyword lets you override that default failure decision using a condition. 

- name: Check a directory
  ansible.builtin.command:
    cmd: test -d /tmp/learning-labs
  register: directory_result
  changed_when: false
  failed_when: directory_result.rc != 0

In this example:

  • test -d checks whether the directory exists.
  • register stores the task result.
  • changed_when: false reports that this check does not change the system.
  • failed_when marks the task as failed if the return code is not zero.

2. How failed_when Works

Condition result Ansible task status
True Failed
False Not failed

The condition is evaluated using the result returned by the task.

3. Basic Syntax

- name: Task name
  ansible.builtin.command:
    cmd: your-command
  register: command_result
  failed_when: command_result.rc != 0

You can use registered result attributes such as:

Attribute Purpose
rc Command return code.
stdout Standard output.
stderr Standard error output.
stdout_lines Standard output split into lines.

4. Example: Fail When Output Contains ERROR

A command can return exit code zero but still produce output that your automation considers an error. You can define that condition explicitly. 

---
- name: Demonstrate failed_when with output
  hosts: ansible-client
  become: true

  tasks:
    - name: Generate test output
      ansible.builtin.command:
        cmd: /usr/bin/printf ERROR
      register: output_result
      changed_when: false
      failed_when: "'ERROR' in output_result.stdout"

The command returns ERROR. The condition evaluates to true, so Ansible marks the task as failed even though the command itself returns exit code zero.

5. Example: Allow an Expected Return Code

Sometimes a non-zero return code is an expected result. For example, checking whether an optional directory exists can return code 1 when the directory is absent. 

---
- name: Check an optional directory
  hosts: ansible-client
  become: true

  tasks:
    - name: Check optional directory
      ansible.builtin.command:
        cmd: test -d /tmp/optional-directory
      register: optional_directory_result
      changed_when: false
      failed_when: optional_directory_result.rc not in [0, 1]

    - name: Display check result
      ansible.builtin.debug:
        msg: "Return code: {{ optional_directory_result.rc }}"

Here:

  • Return code 0 means the directory exists.
  • Return code 1 means the directory does not exist.
  • Other return codes are treated as failures.
Important: Allowing a return code through failed_when does not mean the command succeeded. It means you have explicitly defined that result as acceptable for this task.

6. Multiple Conditions with failed_when

You can define multiple conditions using a YAML list. When written as separate list entries, Ansible combines them using logical AND. All conditions must be true for the task to be marked as failed. 

- name: Check command result
  ansible.builtin.command:
    cmd: /usr/bin/printf ERROR
  register: result
  changed_when: false
  failed_when:
    - result.rc == 0
    - "'ERROR' in result.stdout"

The task fails only when both conditions are true.

If you want logical OR, write the expression explicitly: 

failed_when: result.rc != 0 or "'ERROR' in result.stdout"
Remember: Separate entries in a failed_when list use AND, not OR.

7. Difference Between failed_when and changed_when

Keyword Purpose
failed_when Controls whether a task is considered failed.
changed_when Controls whether a task is reported as changed.

These keywords control different aspects of a task result. A task can be successful without reporting a change, or it can be marked as failed based on your custom condition.

8. Difference Between failed_when and ignore_errors

These keywords solve different problems:

  • failed_when defines the condition under which a task is considered failed.
  • ignore_errors allows the play to continue after a task has failed.

We will cover ignore_errors separately in the next lesson.

9. Practical Lab: Validate an Application Check

Scenario

You need to check an application status command. The automation must fail if the output contains the word FAILED.

Create this playbook:

---
- name: Application status validation
  hosts: ansible-client
  become: true

  tasks:
    - name: Generate application status
      ansible.builtin.command:
        cmd: /usr/bin/printf "Application RUNNING"
      register: application_status
      changed_when: false
      failed_when: "'FAILED' in application_status.stdout"

    - name: Display application status
      ansible.builtin.debug:
        msg: "{{ application_status.stdout }}"

Run from ansible-controller:

ansible-playbook application-status.yml

Expected behavior:

  • The command produces Application RUNNING.
  • The failure condition evaluates to false.
  • The task completes successfully.
  • The status is displayed by the debug task.

Change the command output from Application RUNNING to Application FAILED and run the playbook again. The first task should now be marked as failed.

Why Do We Use the Ansible failed_when Keyword?

In real DevOps automation, a command's return code does not always represent the complete operational result. Some commands return zero even when their output contains an application-level error. Other commands return non-zero codes for conditions that are expected and acceptable.

The failed_when keyword gives you control over how Ansible interprets these results. You can validate application output, inspect return codes, and define precise failure conditions for your automation.

For example, while performing application health checks, deployment validation, service verification, or infrastructure checks, you can decide exactly when Ansible should stop treating a task as successful.

This makes playbooks more reliable because failure decisions are based on the actual conditions that matter to your automation, rather than only on the command's default exit status.
