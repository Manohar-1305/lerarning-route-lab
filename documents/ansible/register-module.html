Ansible Register Keyword

The Ansible register keyword captures the result of a task and stores it in a variable. That variable can then be used by subsequent tasks to make decisions, display output or validate results.

1. What Is Register?

In Ansible, register is a playbook keyword used to save the result returned by a task.

When a task executes, Ansible produces a result containing information about the execution. Depending on the module, this may include:

  • Standard output (stdout).
  • Standard error (stderr).
  • Return code (rc).
  • Whether the task changed something (changed).
  • Whether the task failed (failed).
  • Module-specific returned information.

The register keyword stores this result in a variable that later tasks can access.

2. How Does Register Work?

             Ansible Controller
             ------------------
                    |
                    v
                Playbook
                    |
                    v
                Execute Task
                    |
                    v
             Task Returns Result
                    |
                    v
             register: result
                    |
                    v
             Store Result Variable
                    |
                    v
             Next Task Uses Variable

For example, a task can execute a command to retrieve the hostname. Ansible stores the result in a variable, which a later task can use to display the hostname.

3. Basic Register Syntax

The register keyword is written at the same indentation level as the module used in the task. 

---
- name: Register example
  hosts: ansible-client
  become: true

  tasks:
    - name: Get hostname
      ansible.builtin.command:
        cmd: hostname
      register: hostname_result

Here, hostname_result is the variable containing the result of the hostname task.

Important: register is not an Ansible module. It is a playbook keyword that captures a task result.

4. Understanding the Registered Result

A registered variable is a dictionary containing fields returned by the task.

For a successful Command or Shell task, commonly available fields include:

Field Description
stdout Standard output returned by the command.
stdout_lines Standard output split into individual lines.
stderr Standard error returned by the command.
stderr_lines Standard error split into individual lines.
rc Command return code. Usually zero indicates success.
changed Indicates whether Ansible reports the task as changed.
failed Indicates whether the task failed.
cmd The command that was executed.

The exact fields depend on the module. Do not assume every module returns all these fields.

5. Capture and Display Command Output

This example captures the hostname and displays the output using the Debug module.

Playbook: register-hostname.yml

---
- name: Capture hostname
  hosts: ansible-client
  become: true

  tasks:
    - name: Get managed host hostname
      ansible.builtin.command:
        cmd: hostname
      register: hostname_result
      changed_when: false

    - name: Display hostname
      ansible.builtin.debug:
        msg: "Managed host hostname is {{ hostname_result.stdout }}"

The hostname command result is stored in hostname_result. The next task accesses its stdout field.

6. Access stdout and stdout_lines

The stdout field contains the complete standard output as a string. The stdout_lines field contains the output as a list of lines.

Playbook: register-output.yml

---
- name: Capture command output
  hosts: ansible-client
  become: true

  tasks:
    - name: Get filesystem information
      ansible.builtin.command:
        cmd: df -h
      register: disk_result
      changed_when: false

    - name: Display complete output
      ansible.builtin.debug:
        var: disk_result.stdout

    - name: Display output line by line
      ansible.builtin.debug:
        var: disk_result.stdout_lines

7. Access the Return Code

The rc field contains the return code of a command. A return code of 0 usually indicates success. A non-zero return code usually indicates an error.

Playbook: register-return-code.yml

---
- name: Check command return code
  hosts: ansible-client
  become: true

  tasks:
    - name: Check whether a directory exists
      ansible.builtin.command:
        cmd: test -d /tmp/learning-labs
      register: directory_result
      changed_when: false
      failed_when: false

    - name: Display return code
      ansible.builtin.debug:
        msg: "Return code is {{ directory_result.rc }}"

The test -d command returns zero when the directory exists and a non-zero value when it does not.

8. Register Results from Multiple Tasks

You can use different registered variables to capture the results of multiple tasks in the same playbook.

Playbook: register-multiple.yml

---
- name: Collect Linux system information
  hosts: ansible-client
  become: true

  tasks:
    - name: Get hostname
      ansible.builtin.command:
        cmd: hostname
      register: hostname_result
      changed_when: false

    - name: Get current date
      ansible.builtin.command:
        cmd: date
      register: date_result
      changed_when: false

    - name: Get kernel version
      ansible.builtin.command:
        cmd: uname -r
      register: kernel_result
      changed_when: false

    - name: Display system information
      ansible.builtin.debug:
        msg:
          - "Hostname: {{ hostname_result.stdout }}"
          - "Date: {{ date_result.stdout }}"
          - "Kernel: {{ kernel_result.stdout }}"

9. Register Results from the Copy Module

Register can capture results from Ansible modules, not only Command and Shell tasks.

The following example captures the result of a file-copy operation.

Playbook: register-copy.yml

---
- name: Capture copy module result
  hosts: ansible-client
  become: true

  tasks:
    - name: Create application configuration
      ansible.builtin.copy:
        content: |
          APP_NAME=learning-labs
          APP_PORT=8080
        dest: /tmp/learning-labs.conf
        mode: '0644'
      register: copy_result

    - name: Display copy operation result
      ansible.builtin.debug:
        var: copy_result

The registered result may include information such as the destination path, checksum and changed status.

Important: If the file already has the requested content and attributes, the Copy module can report changed: false. This demonstrates Ansible idempotency.

10. Use Register with a Failed Command

By default, a task that returns a non-zero command return code fails. If you want to inspect that result in a later task, you can use failed_when: false.

Playbook: register-failure.yml

---
- name: Capture command failure
  hosts: ansible-client
  become: true

  tasks:
    - name: Check a non-existent directory
      ansible.builtin.command:
        cmd: test -d /tmp/non-existent-directory
      register: check_result
      changed_when: false
      failed_when: false

    - name: Display command status
      ansible.builtin.debug:
        msg: "Command return code: {{ check_result.rc }}"

The task is allowed to continue even when the command returns a non-zero code. The result remains available in check_result.

11. Register Results from a Loop

When a task uses a loop and register, Ansible stores the individual task results in a results list.

Playbook: register-loop.yml

---
- name: Register results from multiple commands
  hosts: ansible-client
  become: true

  tasks:
    - name: Check important directories
      ansible.builtin.command:
        cmd: "test -d {{ item }}"
      loop:
        - /tmp
        - /etc
        - /var
      register: directory_checks
      changed_when: false
      failed_when: false

    - name: Display all directory check results
      ansible.builtin.debug:
        var: directory_checks.results

Each item produces an individual result. The results are collected inside directory_checks.results.

12. Register and Reuse Results in Another Task

A registered result can be used in later tasks to make decisions.

Playbook: register-reuse.yml

---
- name: Reuse registered result
  hosts: ansible-client
  become: true

  tasks:
    - name: Get hostname
      ansible.builtin.command:
        cmd: hostname
      register: hostname_result
      changed_when: false

    - name: Display hostname result
      ansible.builtin.debug:
        msg: "The hostname is {{ hostname_result.stdout }}"

    - name: Display command return code
      ansible.builtin.debug:
        msg: "Command completed with return code {{ hostname_result.rc }}"

13. Register and Assert

The Assert module can validate values captured by a previous task. This is useful when a deployment depends on a command returning an expected result.

Playbook: register-assert.yml

---
- name: Validate registered command result
  hosts: ansible-client
  become: true

  tasks:
    - name: Get hostname
      ansible.builtin.command:
        cmd: hostname
      register: hostname_result
      changed_when: false

    - name: Validate hostname is not empty
      ansible.builtin.assert:
        that:
          - hostname_result.stdout | length > 0
        success_msg: "Hostname validation passed."
        fail_msg: "Hostname information is empty."

This example uses the registered hostname output as the input to an assertion.

14. Practical Project: Linux Server Information Collector

Project Objective

Build a playbook that collects information from a Linux managed host, stores each result in a registered variable and generates a report.

Requirements:
  1. Collect the hostname.
  2. Collect the kernel version.
  3. Collect the current date.
  4. Collect root filesystem usage.
  5. Capture all command outputs using register.
  6. Validate that the hostname is not empty.
  7. Display the collected information.
Project playbook: server-information.yml 
---
- name: Collect Linux server information
  hosts: ansible-client
  become: true

  tasks:
    - name: Collect hostname
      ansible.builtin.command:
        cmd: hostname
      register: hostname_result
      changed_when: false

    - name: Collect kernel version
      ansible.builtin.command:
        cmd: uname -r
      register: kernel_result
      changed_when: false

    - name: Collect current date
      ansible.builtin.command:
        cmd: date
      register: date_result
      changed_when: false

    - name: Collect root filesystem usage
      ansible.builtin.command:
        cmd: df -h /
      register: disk_result
      changed_when: false

    - name: Validate hostname
      ansible.builtin.assert:
        that:
          - hostname_result.stdout | length > 0
        success_msg: "Hostname validation passed."
        fail_msg: "Hostname information is missing."

    - name: Display server information
      ansible.builtin.debug:
        msg:
          - "Hostname: {{ hostname_result.stdout }}"
          - "Kernel: {{ kernel_result.stdout }}"
          - "Date: {{ date_result.stdout }}"
          - "Disk usage:"
          - "{{ disk_result.stdout }}"

15. Important Considerations

  • register captures a task result in a variable.
  • Registered variables are available to subsequent tasks in the same play.
  • A registered variable is not automatically shared between different hosts.
  • Each host normally has its own registered result.
  • Use unique variable names to avoid overwriting earlier results.
  • Command and Shell modules commonly return stdout, stderr and rc.
  • Other modules return their own module-specific result fields.
  • For looped tasks, individual results are available under the registered variable's results field.
  • A failed task can still have a registered result, but execution normally stops for that host unless failure handling is configured.
  • Registered variables are runtime data, not persistent storage between separate playbook runs.

Why Do We Use the Register Keyword?

In real-world DevOps environments, executing a task is not always enough. Engineers often need to capture its output and use that information to decide what should happen next.

For example, during a server deployment, an engineer may need to retrieve the hostname, check a command's return code, inspect disk usage or capture the result of a configuration change.

The Register keyword stores task results in variables, allowing subsequent tasks to access and process that information.

It is commonly used in infrastructure validation, deployment automation, troubleshooting, conditional execution and operational report generation.

Register is particularly useful when combined with other Ansible features such as Debug, Assert and When.
