Ansible User Module

In this lab, you will learn how to manage Linux user accounts using the Ansible User module. You will create users, configure their home directories and login shells, modify existing accounts, and remove users through Ansible playbooks.

At the end, you will build a practical project that automates the creation and management of application user accounts.

1. What Is the User Module?

Linux uses user accounts to identify individuals and processes that interact with the operating system. Each user has a username, user ID (UID), primary group, home directory and login shell.

The Ansible User module allows administrators to create, modify and delete user accounts on managed Linux systems.

The module is useful when you need to manage user accounts consistently across multiple servers without manually creating each account.

The fully qualified module name is: 

ansible.builtin.user

2. User Module Syntax

The basic structure of the User module looks like this: 

- name: Create a Linux user
  ansible.builtin.user:
    name: devops
    state: present

ansible.builtin.user identifies the module. The name parameter specifies the account, and state defines whether the account should exist or be absent.

3. Important User Module Parameters

name

Specifies the username that Ansible should manage. 

name: devops

In this example, Ansible manages an account named devops.

state

Specifies the desired state of the user account.

  • present – Ensures that the user account exists.
  • absent – Ensures that the user account is removed.

When state: present is used, Ansible creates the account if it does not exist. If it already exists, Ansible checks whether its requested attributes need modification.

uid

Specifies the numeric user ID assigned to the account. Every Linux user has a UID that identifies the account internally. 

uid: 1050

In this example, the user is assigned UID 1050. If the UID is already assigned to another account, the creation may fail unless the configuration is adjusted.

comment

Adds descriptive information to the user account. This is commonly used to store the user's full name or role. 

comment: "DevOps Engineer"

The comment is stored in the user account information and can be viewed through Linux account management commands.

home

Specifies the home directory path for the user. 

home: /home/devops

The home directory is the user's personal directory. It is commonly used to store configuration files, scripts and user-specific data.

create_home

Controls whether Ansible creates the user's home directory when the account is created. 

create_home: true

When set to true, Ansible creates the home directory if it does not already exist.

When set to false, the home directory is not automatically created.

shell

Specifies the login shell assigned to the user. 

shell: /bin/bash

This assigns Bash as the user's login shell. The user can interact with the system through this shell when logging in.

You can also assign a non-login shell: 

shell: /usr/sbin/nologin

A non-login shell prevents the account from starting a normal interactive login session. This is useful for service accounts that need an identity but should not have interactive access.

groups

Specifies the supplementary groups to which the user should belong. 

groups:
  - developers
  - monitoring

This assigns the user to the supplementary groups developers and monitoring.

The groups must already exist unless you separately create them using an appropriate group management task.

append

Controls whether the groups specified in the groups parameter are added to the user's existing supplementary groups or replace the existing supplementary group list. 

groups:
  - developers
  - monitoring
append: true

With append: true, the specified groups are added without removing the user's other supplementary group memberships.

With append: false, which is the default behavior, the supplementary group list is managed according to the groups specified in the playbook.

password

Specifies the encrypted password for the user account. Linux expects a password hash rather than an ordinary plain-text password. 

password: "$6$example_encrypted_password_hash"

The value above is only an illustrative placeholder. It is not a usable password hash.

Never store plain-text passwords directly in a playbook. Use Ansible Vault or another approved secret-management mechanism to protect password hashes and sensitive information.

password_lock

Controls whether the user's password is locked. 

password_lock: true

A locked password prevents password-based authentication using that account password. It does not necessarily disable every other authentication method.

remove

Controls whether the user's home directory and associated files are removed when deleting the account. 

state: absent
remove: true

When used with state: absent, this requests removal of the user's home directory and related files.

Removing a user with remove: true can permanently delete personal data. Confirm that the account's files are no longer required before using this option.

4. Create a Single User

Create a playbook named create-user.yml. In this example, you will create a user named devops. 

---
- name: Create Linux User
  hosts: localhost
  connection: local
  become: true

  tasks:
    - name: Create devops user
      ansible.builtin.user:
        name: devops
        state: present
        shell: /bin/bash
        create_home: true

Understanding the Playbook

hosts: localhost targets the local Ubuntu system.

connection: local tells Ansible to execute the tasks locally rather than connecting through SSH.

become: true enables administrative privileges because creating a Linux user requires elevated permissions.

name: devops specifies the account to create.

state: present ensures that the account exists.

shell: /bin/bash assigns Bash as the login shell.

create_home: true creates the user's home directory when required.

5. Create a User with Specific UID and Details

You can provide additional information while creating a user. Create create-user-details.yml. 

---
- name: Create User with Specific Details
  hosts: localhost
  connection: local
  become: true

  tasks:
    - name: Create application administrator
      ansible.builtin.user:
        name: appadmin
        uid: 1050
        comment: "Application Administrator"
        home: /home/appadmin
        create_home: true
        shell: /bin/bash
        state: present

Understanding the Playbook

name: appadmin creates or manages the appadmin account.

uid: 1050 assigns the requested numeric user ID.

comment adds descriptive information to the account.

home specifies the home directory path.

create_home: true ensures that the home directory is created when needed.

shell: /bin/bash assigns Bash as the login shell.

6. Create Multiple Users

Ansible allows you to create multiple users using a loop. This is useful when several team members require accounts.

Create create-multiple-users.yml. 

---
- name: Create Multiple Linux Users
  hosts: localhost
  connection: local
  become: true

  tasks:
    - name: Create application team users
      ansible.builtin.user:
        name: "{{ item }}"
        state: present
        shell: /bin/bash
        create_home: true
      loop:
        - developer1
        - developer2
        - tester1

Understanding the Playbook

loop allows a task to execute repeatedly for each item in a list.

item represents the current value being processed by the loop.

During execution, Ansible creates the following accounts:

  • developer1
  • developer2
  • tester1

Each account receives a Bash login shell and a home directory.

7. Modify an Existing User

The User module can modify an existing account. For example, you can change the user's login shell, comment or supplementary groups.

Create modify-user.yml. 

---
- name: Modify Existing Linux User
  hosts: localhost
  connection: local
  become: true

  tasks:
    - name: Update devops user details
      ansible.builtin.user:
        name: devops
        comment: "Senior DevOps Engineer"
        shell: /bin/bash
        state: present

Understanding the Playbook

The task identifies the existing account using name: devops.

The comment parameter updates the descriptive information associated with the account.

The shell parameter ensures that the user has the requested login shell.

The module modifies the existing account instead of creating a separate account.

8. Add a User to Supplementary Groups

Users can belong to supplementary groups to receive additional permissions. The User module can manage these group memberships.

Create assign-user-groups.yml. 

---
- name: Assign User to Supplementary Groups
  hosts: localhost
  connection: local
  become: true

  tasks:
    - name: Add devops user to existing groups
      ansible.builtin.user:
        name: devops
        groups:
          - adm
          - sudo
        append: true
        state: present

Understanding the Playbook

groups specifies the supplementary groups to which the devops user should belong.

adm and sudo are commonly available Ubuntu groups, but their existence should be verified on the target system.

append: true preserves existing supplementary group memberships while adding the specified groups.

Adding a user to the sudo group grants administrative privileges on Ubuntu. Only assign this membership to accounts that legitimately require it.

9. Create a Service Account

Not every Linux account is intended for an individual to log in. Applications and services often use dedicated service accounts.

These accounts can have restricted login capabilities. Create create-service-user.yml. 

---
- name: Create Application Service Account
  hosts: localhost
  connection: local
  become: true

  tasks:
    - name: Create application service user
      ansible.builtin.user:
        name: appservice
        system: true
        create_home: false
        shell: /usr/sbin/nologin
        state: present

Understanding the Playbook

name: appservice identifies the service account.

system: true requests a system account rather than a regular user account. The UID is selected from the system account range according to the operating system's account configuration.

create_home: false prevents automatic creation of a home directory.

shell: /usr/sbin/nologin assigns a non-login shell. This prevents normal interactive login through that shell.

state: present ensures that the service account exists.

10. Delete a User

The User module can remove an existing Linux account. Create delete-user.yml. 

---
- name: Delete Linux User
  hosts: localhost
  connection: local
  become: true

  tasks:
    - name: Remove developer1 user
      ansible.builtin.user:
        name: developer1
        state: absent

Understanding the Playbook

name: developer1 identifies the account.

state: absent requests removal of the user account.

By default, the user's home directory and files are not automatically deleted.

If you also need to remove the user's home directory and related files, use remove: true.

11. Verify User Accounts

After executing a playbook, you can inspect the Linux account information to confirm that the user was created.

Check the user account:

id devops

This displays the UID, primary group and supplementary group memberships of the account.

View the user's account entry:

getent passwd devops

This displays the account information, including username, UID, GID, home directory and login shell.

Check the home directory:

ls -ld /home/devops

This displays the directory details and ownership.

12. Practical Project: Linux Application Account Management

In this project, you will automate the creation of application and development user accounts using the Ansible User module.

You will create a playbook that manages different types of accounts, assigns account details, creates home directories and configures login shells.

Project Requirements

  • Create a user named appadmin.
  • Assign UID 1501 to appadmin.
  • Set the comment to Application Administrator.
  • Create the appadmin home directory.
  • Create developer1 and developer2 accounts.
  • Assign Bash as the developers' login shell.
  • Create an appservice system account.
  • Disable interactive login for appservice.
  • Ensure all requested accounts exist.

Step 1: Create the Project Directory

mkdir -p linux-user-management
cd linux-user-management

Step 2: Create the Main Playbook

Create a file named user-management.yml. 

---
- name: Linux Application User Management
  hosts: localhost
  connection: local
  become: true

  tasks:

    - name: Create application administrator
      ansible.builtin.user:
        name: appadmin
        uid: 1501
        comment: "Application Administrator"
        home: /home/appadmin
        create_home: true
        shell: /bin/bash
        state: present

    - name: Create developer accounts
      ansible.builtin.user:
        name: "{{ item }}"
        create_home: true
        shell: /bin/bash
        state: present
      loop:
        - developer1
        - developer2

    - name: Create application service account
      ansible.builtin.user:
        name: appservice
        system: true
        create_home: false
        shell: /usr/sbin/nologin
        state: present

Step 3: Understand the Project Playbook

The first task creates the application administrator account with a specific UID, comment, home directory and login shell.

The second task uses a loop to create two developer accounts. Both accounts receive their own home directories and Bash shells.

The third task creates a system account for the application. It does not create a home directory and uses a non-login shell.

All three tasks use the same User module but configure different account requirements.

Step 4: Validate the Playbook

Validate the YAML syntax and playbook structure. 

ansible-playbook user-management.yml --syntax-check

Step 5: Execute the Playbook

ansible-playbook user-management.yml

Ansible executes the three tasks and ensures that all four requested accounts exist with their configured properties.

Step 6: Verify the Administrator Account

id appadmin
getent passwd appadmin
ls -ld /home/appadmin

Step 7: Verify Developer Accounts

id developer1
id developer2

getent passwd developer1
getent passwd developer2

Step 8: Verify the Service Account

getent passwd appservice

Check that the service account uses /usr/sbin/nologin as its login shell.

Step 9: Execute the Playbook Again

Run the same playbook again: 

ansible-playbook user-management.yml

Since the requested accounts and their attributes are already configured, Ansible should report ok for tasks that do not require further changes.

Project completed: You have automated Linux user account management using the Ansible User module.

Why Do We Use the Ansible User Module?

Linux user management is an important part of system administration. Every user and application that requires access to a Linux system needs an appropriate account with the required permissions and configuration.

In organizations managing multiple Linux servers, administrators frequently need to create accounts, modify user information, assign group memberships and remove accounts when they are no longer required.

Performing these activities manually on every server increases administrative effort and can result in inconsistent account configurations.

The Ansible User module automates these activities through playbooks, allowing administrators to manage accounts consistently across managed systems.

1. Centralized User Account Management

Consider an organization with multiple application servers. A new developer joins the team and requires an account on every server.

Without automation, an administrator would need to create the account individually on each server and configure the home directory and login shell.

With the Ansible User module, the administrator defines the required account configuration in a playbook and executes it against the selected servers.

This reduces repetitive manual account management.

2. Consistent User Configuration

User accounts should follow organizational standards. For example, every developer account may require a home directory and Bash as the login shell.

The User module allows administrators to define these requirements and apply them consistently.

This helps avoid differences in account configuration between servers.

3. Automated User Provisioning

User provisioning is the process of creating and configuring accounts when a new employee, administrator or application requires access.

The User module can automate account creation, assign user IDs, configure home directories and specify login shells.

This is particularly useful during initial server configuration and application deployment.

4. Managing Application Service Accounts

Applications often need dedicated Linux accounts to run processes. These accounts should generally have only the access required by the application.

The User module supports creating system accounts and assigning restricted login shells.

For example, an application service account can be created with system: true, no automatically created home directory and /usr/sbin/nologin as its shell.

This separates application identities from regular interactive user accounts.

5. Managing User Access

User accounts can belong to supplementary groups that determine access to particular resources and operations.

The User module can manage supplementary group membership. This allows administrators to add users to the groups required for their responsibilities.

For example, an authorized administrator may need membership in the sudo group, while a developer may need membership in an application-specific group.

Group membership should always follow the organization's access control policy.

6. Automated Account Deprovisioning

When an employee leaves an organization or an application no longer requires an account, the account may need to be removed.

The User module supports account removal using state: absent.

Administrators can also request removal of the user's home directory and related files using remove: true.

Before deleting accounts or their data, administrators should verify ownership, retention requirements and backup requirements.

7. Idempotency and Repeatable Automation

The User module supports idempotent configuration. When a playbook requests that a user account exists, Ansible checks whether the account is already present.

If the account exists with the requested configuration, Ansible does not need to recreate it.

If the account is missing or its requested attributes differ, Ansible applies the required changes.

This makes user management repeatable and predictable.

8. Why Is This Important for a DevOps Engineer?

DevOps engineers work with server provisioning, application deployments, automation and infrastructure maintenance. These activities frequently require dedicated service accounts and controlled user access.

Understanding the User module helps automate account provisioning, standardize user configuration and manage application identities.

It also provides a foundation for more advanced access management workflows involving groups, permissions, SSH keys and configuration management.
