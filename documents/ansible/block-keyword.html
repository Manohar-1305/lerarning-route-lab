Ansible block Keyword

The block keyword allows you to group multiple tasks together under a single logical section. You can organize related operations and apply common task-level settings to the entire group.

1. What Is block?

In a normal Ansible playbook, tasks are written individually under the tasks section.

When several tasks belong to the same operation, you can group them inside a block.

For example, preparing an application environment may involve:

  • Creating an application directory.
  • Creating a configuration file.
  • Creating a log directory.
  • Verifying the application configuration.

Instead of treating these as unrelated tasks, you can group them inside one block.

2. Basic Syntax

---
- name: Demonstrate block
  hosts: ansible-client
  become: true

  tasks:
    - name: Application preparation
      block:
        - name: Task 1
          ansible.builtin.debug:
            msg: "First task"

        - name: Task 2
          ansible.builtin.debug:
            msg: "Second task"

        - name: Task 3
          ansible.builtin.debug:
            msg: "Third task"

The tasks inside the block execute sequentially, just like normal Ansible tasks.

3. Understanding Block Execution

Consider a block containing three tasks: 

tasks:
  - name: Application setup
    block:
      - name: Create directory
        ansible.builtin.file:
          path: /opt/myapp
          state: directory

      - name: Create configuration
        ansible.builtin.copy:
          content: "APP_PORT=8080\n"
          dest: /opt/myapp/app.conf

      - name: Display completion
        ansible.builtin.debug:
          msg: "Application setup completed"

Ansible executes the tasks in this order:

Order Task
1 Create directory
2 Create configuration
3 Display completion

The block provides a logical grouping. It does not execute all tasks simultaneously.

4. Apply Common Settings to a Block

One important advantage of block is that you can apply common task-level settings to the grouped tasks.

For example, you can apply become to the block instead of repeating it in every task. 

---
- name: Block with privilege escalation
  hosts: ansible-client

  tasks:
    - name: Application setup
      become: true
      block:
        - name: Create application directory
          ansible.builtin.file:
            path: /opt/myapp
            state: directory
            mode: '0755'

        - name: Create log directory
          ansible.builtin.file:
            path: /var/log/myapp
            state: directory
            mode: '0755'

        - name: Create configuration file
          ansible.builtin.copy:
            content: "APP_ENV=production\n"
            dest: /opt/myapp/app.conf
            mode: '0644'

The privilege escalation setting applies to the tasks inside the block. You do not need to repeat become: true for each task.

5. Apply Variables to a Block

You can define variables at the block level. Tasks inside the block can use those variables. 

---
- name: Block with variables
  hosts: ansible-client
  become: true

  tasks:
    - name: Configure application
      vars:
        app_name: learning-labs
        app_port: 8080
        app_directory: /opt/learning-labs
      block:
        - name: Create application directory
          ansible.builtin.file:
            path: "{{ app_directory }}"
            state: directory
            mode: '0755'

        - name: Create application configuration
          ansible.builtin.copy:
            content: |
              APP_NAME={{ app_name }}
              APP_PORT={{ app_port }}
            dest: "{{ app_directory }}/app.conf"
            mode: '0644'

        - name: Display configuration location
          ansible.builtin.debug:
            msg: "Configuration created at {{ app_directory }}/app.conf"

The variables defined at the block level are available to the tasks inside that block.

6. Apply Conditions to a Block

You can also apply a condition to a block using the when keyword.

The condition is evaluated for the tasks inside the block. 

---
- name: Conditional block
  hosts: ansible-client
  become: true

  vars:
    deploy_application: true

  tasks:
    - name: Deploy application files
      when: deploy_application
      block:
        - name: Create application directory
          ansible.builtin.file:
            path: /opt/myapp
            state: directory

        - name: Create application configuration
          ansible.builtin.copy:
            content: "APP_ENV=production\n"
            dest: /opt/myapp/app.conf

        - name: Display deployment message
          ansible.builtin.debug:
            msg: "Application deployment tasks executed"

If deploy_application is true, the block tasks execute. If it is false, the tasks are skipped.

7. Block-Level Tags

You can assign a tag to a block. The tag is inherited by the tasks inside that block. 

---
- name: Block with tags
  hosts: ansible-client
  become: true

  tasks:
    - name: Application configuration
      tags:
        - application_setup
      block:
        - name: Create application directory
          ansible.builtin.file:
            path: /opt/myapp
            state: directory

        - name: Create configuration file
          ansible.builtin.copy:
            content: "APP_PORT=8080\n"
            dest: /opt/myapp/app.conf

        - name: Display completion
          ansible.builtin.debug:
            msg: "Application configuration completed"

You can run the tagged block from ansible-controller: 

ansible-playbook application-block.yml --tags application_setup

This executes the tasks associated with the specified tag.

8. Block Does Not Automatically Handle Errors

A block groups tasks, but it does not automatically recover from a failed task.

For example, if the second task fails, Ansible normally stops executing the remaining tasks in that block for the affected host. 

---
- name: Block failure demonstration
  hosts: ansible-client
  become: true

  tasks:
    - name: Demonstrate task failure inside a block
      block:
        - name: First task
          ansible.builtin.debug:
            msg: "First task executed"

        - name: Second task
          ansible.builtin.command:
            cmd: /bin/false

        - name: Third task
          ansible.builtin.debug:
            msg: "Third task executed"

The first task executes. The second task fails. The third task does not execute.

Important: Error recovery using rescue and guaranteed cleanup using always are separate concepts. They will be covered in their own lessons.

9. Practical Lab: Prepare an Application Environment Using block

Scenario

You need to prepare an application environment on ansible-client. All related preparation tasks should be grouped under one block.

Create this playbook:

---
- name: Prepare application environment
  hosts: ansible-client
  become: true

  tasks:
    - name: Application environment setup
      vars:
        app_name: learning-labs
        app_directory: /opt/learning-labs
        app_port: 8080
      block:

        - name: Create application directory
          ansible.builtin.file:
            path: "{{ app_directory }}"
            state: directory
            owner: root
            group: root
            mode: '0755'

        - name: Create logs directory
          ansible.builtin.file:
            path: "{{ app_directory }}/logs"
            state: directory
            mode: '0755'

        - name: Create configuration file
          ansible.builtin.copy:
            content: |
              APP_NAME={{ app_name }}
              APP_PORT={{ app_port }}
              APP_ENV=production
            dest: "{{ app_directory }}/app.conf"
            mode: '0644'

        - name: Display configuration location
          ansible.builtin.debug:
            msg: "Configuration created at {{ app_directory }}/app.conf"

        - name: Verify configuration file
          ansible.builtin.command:
            cmd: test -f "{{ app_directory }}/app.conf"
          changed_when: false

Run from ansible-controller:

ansible-playbook application-block.yml

Expected behavior:

  • The application directory is created.
  • The logs directory is created.
  • The application configuration file is created.
  • The configuration location is displayed.
  • The configuration file is verified.

Why Do We Use the Ansible block Keyword?

In real DevOps environments, a single automation workflow often contains several related operations. For example, application deployment may involve creating directories, configuring files, setting permissions, and validating the deployment.

Writing these operations as unrelated tasks can make large playbooks difficult to organize and maintain.

The block keyword allows you to group related tasks into a logical section. You can also apply common settings such as privilege escalation, variables, and conditions to the grouped tasks instead of repeating them individually.

This makes playbooks easier to read, maintain, and extend. It also provides the structure needed for more advanced error handling workflows, which can be built using the separate rescue and always sections.
