Ansible Handlers

Ansible handlers are special tasks that execute only when another task notifies them. They are commonly used for operations such as restarting a service, reloading an application, or applying configuration changes.

1. What Are Handlers?

Normally, Ansible executes tasks sequentially. A handler behaves differently: it runs only when a task explicitly notifies it and that task reports a change.

For example, imagine that you update an Nginx configuration file. There is no need to restart Nginx if the configuration file has not changed. You can notify a handler to restart or reload the service only when Ansible detects a change.

2. Basic Handler Syntax

---
- name: Demonstrate handlers
  hosts: ansible-client
  become: true

  tasks:
    - name: Update application configuration
      ansible.builtin.copy:
        content: "application_port=8080\n"
        dest: /tmp/application.conf
        mode: '0644'
      notify: Reload application

  handlers:
    - name: Reload application
      ansible.builtin.debug:
        msg: "Application reload handler executed"

This playbook contains two main sections:

  • tasks: Contains normal tasks.
  • handlers: Contains special tasks that can be triggered by notifications.

The task copies configuration content to a file. If the file is created or its content changes, Ansible notifies the handler.

The handler executes at the end of the play, provided the play reaches the handler execution stage.

3. Understanding notify

The notify keyword connects a normal task to a handler. The value of notify must match the handler name. 

tasks:
  - name: Update configuration
    ansible.builtin.copy:
      content: "port=8080\n"
      dest: /tmp/app.conf
    notify: Restart application

handlers:
  - name: Restart application
    ansible.builtin.debug:
      msg: "Restart handler triggered"

In this example:

  1. Ansible executes the configuration task.
  2. If the file changes, the task reports changed.
  3. The task notifies the handler.
  4. Ansible executes the handler later in the play.
Important: A handler is not executed simply because a task contains notify. The notifying task must report a change.

4. When Does a Handler Execute?

Handlers normally execute at the end of the current play, after the regular tasks have completed. 

---
- name: Handler execution order
  hosts: ansible-client
  become: true

  tasks:
    - name: Update configuration
      ansible.builtin.copy:
        content: "environment=production\n"
        dest: /tmp/environment.conf
        mode: '0644'
      notify: Apply configuration

    - name: Execute another task
      ansible.builtin.debug:
        msg: "Normal task executed"

    - name: Execute final normal task
      ansible.builtin.debug:
        msg: "Another normal task executed"

  handlers:
    - name: Apply configuration
      ansible.builtin.debug:
        msg: "Handler executed after normal tasks"

The execution order is:

Order Execution
1 Update configuration
2 Execute another task
3 Execute final normal task
4 Execute handler

5. Handler Executes Only When a Change Occurs

Ansible uses the task's changed status to determine whether the handler should be triggered.

Consider this example: 

---
- name: Demonstrate handler change detection
  hosts: ansible-client
  become: true

  tasks:
    - name: Ensure configuration exists
      ansible.builtin.copy:
        content: "application=learning-labs\n"
        dest: /tmp/learning-labs.conf
        mode: '0644'
      notify: Reload application

  handlers:
    - name: Reload application
      ansible.builtin.debug:
        msg: "Configuration changed. Reload required."

Run this playbook for the first time. Ansible creates the file and reports the task as changed. The handler executes.

Run the same playbook again without modifying the content. Ansible reports the copy task as OK because the file already contains the expected content. The handler does not execute.

Execution Copy task Handler
First run Changed Executed
Second run OK Not executed
Content modified Changed Executed

6. Multiple Tasks Can Notify the Same Handler

You can notify the same handler from multiple tasks. If several tasks notify the same handler during one play, Ansible normally executes that handler only once per host. 

---
- name: Multiple notifications
  hosts: ansible-client
  become: true

  tasks:
    - name: Update frontend configuration
      ansible.builtin.copy:
        content: "frontend_port=3000\n"
        dest: /tmp/frontend.conf
      notify: Reload application

    - name: Update backend configuration
      ansible.builtin.copy:
        content: "backend_port=8080\n"
        dest: /tmp/backend.conf
      notify: Reload application

  handlers:
    - name: Reload application
      ansible.builtin.debug:
        msg: "Application reload executed once"

If both files change, both tasks notify the same handler. However, the handler is normally executed only once after the regular tasks complete.

Remember: Handler notifications are deduplicated. Multiple notifications for the same handler do not normally cause multiple executions during the same handler execution cycle.

7. Real-World Example: Restarting a Service

One of the most common uses of handlers is restarting or reloading services after configuration changes.

For example, on a server running Nginx with systemd: 

---
- name: Configure Nginx
  hosts: ansible-client
  become: true

  tasks:
    - name: Update Nginx configuration
      ansible.builtin.copy:
        src: nginx.conf
        dest: /etc/nginx/nginx.conf
        mode: '0644'
      notify: Restart Nginx

  handlers:
    - name: Restart Nginx
      ansible.builtin.service:
        name: nginx
        state: restarted

When the configuration changes, Ansible notifies the handler. The handler restarts Nginx after the normal tasks finish.

Container lab note: The example above assumes Nginx and a service manager are available on the target. Your Ubuntu container may not run systemd. Use the following lab examples for your current container environment.

8. Important Rules About Handlers

  • Handlers are defined under the handlers section of a play.
  • A task triggers a handler using notify.
  • The notification name must match the handler name.
  • A handler runs only when it has been notified by a changed task.
  • Handlers normally execute at the end of the play.
  • Multiple notifications for the same handler are normally combined into one execution per host.
  • Handlers are useful for service restarts, application reloads, and configuration activation.

9. Practical Lab: Application Configuration and Handler

Scenario

You are managing an application configuration file on ansible-client. Whenever the configuration changes, you want Ansible to execute a handler.

Create this playbook:

---
- name: Application configuration management
  hosts: ansible-client
  become: true

  tasks:
    - name: Create application configuration
      ansible.builtin.copy:
        content: |
          APPLICATION_NAME=learning-labs
          APPLICATION_PORT=8080
          APPLICATION_ENV=production
        dest: /tmp/learning-labs.conf
        owner: root
        group: root
        mode: '0644'
      notify: Apply application configuration

    - name: Display normal task message
      ansible.builtin.debug:
        msg: "Application configuration task completed"

    - name: Display another task message
      ansible.builtin.debug:
        msg: "Waiting for handler execution"

  handlers:
    - name: Apply application configuration
      ansible.builtin.command:
        cmd: /usr/bin/printf "Application configuration reload triggered\n"
      changed_when: false

Run from ansible-controller:

ansible-playbook application-handler.yml

Test the behavior:

  1. Run the playbook for the first time.
  2. Observe that the configuration file is created.
  3. Observe that the handler executes after the normal tasks.
  4. Run the playbook again without changing the content.
  5. Observe that the handler does not execute again.
  6. Change APPLICATION_PORT from 8080 to 9090 in the playbook.
  7. Run the playbook again and observe that the handler executes.

The command in this lab simulates an application reload. It does not restart a real application service.

Why Do We Use Ansible Handlers?

In real DevOps environments, configuration changes often require additional actions. Updating an Nginx configuration may require a reload. Changing an application configuration may require a restart. Updating a service configuration may require reloading the service.

Running these operations after every task is inefficient. For example, if a playbook updates five configuration files, restarting the application after every individual file update could cause unnecessary service interruptions.

Ansible handlers solve this problem by allowing tasks to notify a handler only when they report a change. The handler normally executes once after the regular tasks have completed, even if multiple tasks notified it.

This improves automation efficiency, reduces unnecessary service restarts, and helps maintain application availability during configuration management.
