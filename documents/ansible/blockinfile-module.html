Ansible Blockinfile Module

Learn how to insert, update, and remove complete blocks of text inside configuration files using Ansible playbooks.

1. What Is the Blockinfile Module?

The ansible.builtin.blockinfile module manages multiple lines of text inside a file.

It is useful when you need to add an entire configuration section, rather than managing individual lines separately.

For example, an application configuration file may need a complete database configuration section containing several settings. Instead of adding each line individually, you can manage the entire section as one block.

Important: Use lineinfile to manage individual lines. Use blockinfile to manage multiple lines as a block.

2. Understanding Blockinfile Markers

By default, Ansible places marker comments around the block it manages. These markers identify the section that Ansible owns.

For example, a playbook may insert this configuration:

# BEGIN ANSIBLE MANAGED BLOCK
DB_HOST=localhost
DB_PORT=5432
DB_NAME=learning_labs
# END ANSIBLE MANAGED BLOCK

The markers help Ansible locate the block during subsequent playbook executions. When the block content changes, Ansible updates the managed section instead of adding another copy.

3. Basic Playbook Structure

---
- name: Manage configuration block
  hosts: ansible-client
  become: true

  tasks:
    - name: Add database configuration block
      ansible.builtin.blockinfile:
        path: /tmp/app.conf
        block: |
          DB_HOST=localhost
          DB_PORT=5432
          DB_NAME=learning_labs
        state: present
        create: true

Important fields:

  • hosts: Specifies the target managed host.
  • become: Enables privilege escalation.
  • path: Specifies the file to modify.
  • block: Contains the multiple lines to manage.
  • state: Controls whether the block exists.
  • create: Creates the file if it does not exist.

4. Important Parameters

Parameter Description
path Absolute path of the file to modify. Required.
block Multiple lines of content to insert or manage.
state present ensures the block exists. absent removes the managed block.
marker Defines the marker format surrounding the managed block.
marker_begin Customizes the beginning marker text.
marker_end Customizes the ending marker text.
insertafter Inserts the block after a matching expression or at EOF.
insertbefore Inserts the block before a matching expression or at BOF.
backup Creates a backup before modifying the file.
create Creates the target file if it does not exist.
validate Runs a validation command against a temporary file before replacing the target file.
owner Sets the file owner.
group Sets the file group.
mode Sets file permissions.

5. Adding a Multiline Configuration Block

The block parameter accepts multiple lines. YAML's pipe character (|) preserves the line breaks.

Create add-block.yml:

---
- name: Add application configuration block
  hosts: ansible-client
  become: true

  tasks:
    - name: Add database settings
      ansible.builtin.blockinfile:
        path: /tmp/app.conf
        block: |
          DB_HOST=localhost
          DB_PORT=5432
          DB_NAME=learning_labs
          DB_USER=learning_user
        state: present
        create: true

The resulting file contains:

# BEGIN ANSIBLE MANAGED BLOCK
DB_HOST=localhost
DB_PORT=5432
DB_NAME=learning_labs
DB_USER=learning_user
# END ANSIBLE MANAGED BLOCK

6. Updating an Existing Block

If you change the content of the block parameter, Ansible updates the existing managed block.

For example, change the database port to 3306:

---
- name: Update database configuration
  hosts: ansible-client
  become: true

  tasks:
    - name: Update database settings
      ansible.builtin.blockinfile:
        path: /tmp/app.conf
        block: |
          DB_HOST=localhost
          DB_PORT=3306
          DB_NAME=learning_labs
          DB_USER=learning_user
        state: present

Updated content:

# BEGIN ANSIBLE MANAGED BLOCK
DB_HOST=localhost
DB_PORT=3306
DB_NAME=learning_labs
DB_USER=learning_user
# END ANSIBLE MANAGED BLOCK
Ansible identifies the existing block using its markers and updates its contents. It does not create another managed block on every execution.

7. Removing a Managed Block

Set state: absent to remove the block managed by Ansible. 

---
- name: Remove database configuration block
  hosts: ansible-client
  become: true

  tasks:
    - name: Remove database settings
      ansible.builtin.blockinfile:
        path: /tmp/app.conf
        block: |
          DB_HOST=localhost
          DB_PORT=5432
          DB_NAME=learning_labs
          DB_USER=learning_user
        state: absent

Ansible removes the managed block and its markers. Other content outside that block remains untouched.

8. Using Custom Markers

You can customize the marker comments to make managed sections easier to identify. 

---
- name: Add block with custom markers
  hosts: ansible-client
  become: true

  tasks:
    - name: Add custom application block
      ansible.builtin.blockinfile:
        path: /tmp/app.conf
        block: |
          CACHE_ENABLED=true
          CACHE_HOST=localhost
          CACHE_PORT=6379
        marker: "# {mark} APPLICATION CACHE CONFIGURATION"
        state: present
        create: true

Result:

# BEGIN APPLICATION CACHE CONFIGURATION
CACHE_ENABLED=true
CACHE_HOST=localhost
CACHE_PORT=6379
# END APPLICATION CACHE CONFIGURATION
Important: Keep the {mark} placeholder in the marker format. Ansible replaces it with the beginning and ending marker text. If you use the same marker format for multiple independent blocks in one file, Ansible may identify the wrong block.

9. Inserting a Block at a Specific Position

You can control where Ansible inserts a block using insertafter and insertbefore.

Using insertafter

---
- name: Insert block after application section
  hosts: ansible-client
  become: true

  tasks:
    - name: Add logging configuration
      ansible.builtin.blockinfile:
        path: /tmp/app.conf
        block: |
          LOG_LEVEL=INFO
          LOG_FILE=/tmp/application.log
        insertafter: '^APP_NAME='
        state: present

Using insertbefore

---
- name: Insert block before database section
  hosts: ansible-client
  become: true

  tasks:
    - name: Add application metadata
      ansible.builtin.blockinfile:
        path: /tmp/app.conf
        block: |
          APP_OWNER=admin
          APP_VERSION=1.0
        insertbefore: '^DB_HOST='
        state: present

Special insertion positions

  • EOF: End of the file.
  • BOF: Beginning of the file.

10. Creating a Backup Before Modification

Use backup: true to preserve the original file before Ansible modifies it. 

---
- name: Update configuration with backup
  hosts: ansible-client
  become: true

  tasks:
    - name: Update application settings
      ansible.builtin.blockinfile:
        path: /tmp/app.conf
        block: |
          APP_ENV=production
          APP_DEBUG=false
          APP_LOG_LEVEL=INFO
        state: present
        backup: true

11. Using Validate

The validate parameter allows you to check the proposed file content before Ansible replaces the original file.

Ansible creates a temporary file containing the proposed changes and passes its path to the validation command through %s. 

---
- name: Validate configuration before applying
  hosts: ansible-client
  become: true

  tasks:
    - name: Manage application configuration
      ansible.builtin.blockinfile:
        path: /tmp/app.conf
        block: |
          APP_NAME=learning-labs
          APP_PORT=8080
          APP_ENV=production
        state: present
        create: true
        validate: "/usr/bin/test -s %s"

This example checks that the temporary file is not empty. For real applications, use the application's own configuration validation command when one is available.

12. Understanding Idempotency

Idempotency ensures that repeatedly executing the same playbook does not create duplicate configuration blocks.

Consider this task:

- name: Ensure database configuration
  ansible.builtin.blockinfile:
    path: /tmp/app.conf
    block: |
      DB_HOST=localhost
      DB_PORT=5432
      DB_NAME=learning_labs
    state: present
    create: true
  • First execution: Ansible creates the managed block.
  • Second execution: Ansible detects that the block already exists.
  • Third execution: No duplicate block is added.
  • If the block content changes, Ansible updates the managed block.

13. Practical Project: Manage Application Configuration Sections

In this project, you will create an application configuration file and manage separate configuration sections for the application, database, and logging.

Project Requirements

  • Create an application configuration file.
  • Add an application configuration block.
  • Add a database configuration block.
  • Add a logging configuration block.
  • Use custom markers for each block.
  • Update an existing database configuration block.
  • Remove the logging configuration block.
  • Create backups before modifications.

Step 1: Create the Complete Playbook

Create a file named application-config.yml on the Ansible controller. 

---
- name: Manage application configuration sections
  hosts: ansible-client
  become: true

  vars:
    config_dir: /tmp/ansible-blockinfile-lab
    config_file: /tmp/ansible-blockinfile-lab/app.conf

  tasks:

    - name: Create configuration directory
      ansible.builtin.file:
        path: "{{ config_dir }}"
        state: directory
        mode: '0755'

    - name: Create initial configuration file
      ansible.builtin.copy:
        dest: "{{ config_file }}"
        content: |
          # Application configuration
          APP_NAME=learning-labs

          # Additional settings
        force: false
        mode: '0644'

    - name: Add application configuration block
      ansible.builtin.blockinfile:
        path: "{{ config_file }}"
        marker: "# {mark} APPLICATION SETTINGS"
        block: |
          APP_PORT=8080
          APP_ENV=production
          APP_DEBUG=false
        state: present
        backup: true

    - name: Add database configuration block
      ansible.builtin.blockinfile:
        path: "{{ config_file }}"
        marker: "# {mark} DATABASE SETTINGS"
        block: |
          DB_HOST=localhost
          DB_PORT=5432
          DB_NAME=learning_labs
          DB_USER=learning_user
        state: present
        backup: true

    - name: Add logging configuration block
      ansible.builtin.blockinfile:
        path: "{{ config_file }}"
        marker: "# {mark} LOGGING SETTINGS"
        block: |
          LOG_LEVEL=INFO
          LOG_FILE=/tmp/application.log
          LOG_ENABLED=true
        state: present

    - name: Update database configuration block
      ansible.builtin.blockinfile:
        path: "{{ config_file }}"
        marker: "# {mark} DATABASE SETTINGS"
        block: |
          DB_HOST=127.0.0.1
          DB_PORT=5432
          DB_NAME=learning_labs
          DB_USER=learning_user
        state: present
        backup: true

    - name: Remove logging configuration block
      ansible.builtin.blockinfile:
        path: "{{ config_file }}"
        marker: "# {mark} LOGGING SETTINGS"
        state: absent

    - name: Display project completion message
      ansible.builtin.debug:
        msg: "Application configuration blocks have been managed successfully."

Step 2: Expected Configuration

After the playbook completes, the configuration file should contain the following sections: 

# Application configuration
APP_NAME=learning-labs

# Additional settings

# BEGIN APPLICATION SETTINGS
APP_PORT=8080
APP_ENV=production
APP_DEBUG=false
# END APPLICATION SETTINGS

# BEGIN DATABASE SETTINGS
DB_HOST=127.0.0.1
DB_PORT=5432
DB_NAME=learning_labs
DB_USER=learning_user
# END DATABASE SETTINGS

Step 3: Verify the Configuration

Create verify-config.yml on the controller. 

---
- name: Verify application configuration
  hosts: ansible-client
  become: true

  tasks:
    - name: Read application configuration
      ansible.builtin.slurp:
        src: /tmp/ansible-blockinfile-lab/app.conf
      register: config_file_content

    - name: Display application configuration
      ansible.builtin.debug:
        msg: "{{ config_file_content.content | b64decode }}"

Step 4: Test Idempotency

Execute the project playbook again. Ansible should not add duplicate application or database blocks.

Project outcome: You have automated the management of multiple configuration sections on the ansible-client Ubuntu host using blockinfile.

Why Do We Use the Ansible Blockinfile Module?

Linux applications frequently use configuration files that contain multiple related settings. These settings may be grouped into sections for databases, application behavior, logging, caching, security, and other components.

Managing each line separately becomes difficult when an entire configuration section needs to be added, updated, or removed. The blockinfile module solves this problem by allowing administrators to manage multiple lines as one identifiable block.

Ansible uses marker comments to identify the section it manages. This makes it possible to update or remove that section without unnecessarily changing unrelated content in the same file.

Practical Reasons to Use It

  • Manage complete configuration sections: Add multiple related settings together instead of managing each line independently.
  • Update configurations consistently: Maintain standard application, database, and logging sections across multiple managed servers.
  • Remove configuration sections safely: Remove a managed block without deleting unrelated file content.
  • Prevent duplicate blocks: Use markers to identify and maintain the existing managed section.
  • Support deployment automation: Add application-specific configuration sections during deployment workflows.
  • Improve configuration consistency: Apply the same structured configuration to multiple Ubuntu servers.

Real-World DevOps Example

Imagine an organization managing 30 Ubuntu application servers. A new release requires adding a database configuration section containing the database host, port, database name, and username.

Instead of manually editing the configuration file on every server, an administrator can create one Ansible playbook using blockinfile and execute it against the managed inventory.

Ansible inserts the required block, identifies it using markers, and updates the same block when configuration values change.

This makes blockinfile useful for configuration management, application deployment, and infrastructure automation.

Remember: Use blockinfile for multiline sections, lineinfile for individual lines, and template when you need to manage an entire file from a template.
