Ansible import_tasks Module

The import_tasks module allows you to import tasks from another YAML file into your playbook. It helps organize large playbooks by separating tasks into smaller files.

1. Why Do We Need import_tasks?

Imagine you are managing multiple Ubuntu servers using Ansible. Your playbook performs several operations:

  • Create application directories.
  • Install required packages.
  • Create configuration files.
  • Manage file permissions.

Writing all these tasks in one playbook can make it difficult to maintain.

With import_tasks, you can divide the tasks into separate files and import them into your main playbook.

2. Basic Syntax

---
- name: Main playbook
  hosts: ansible-client
  become: true

  tasks:
    - name: Import additional tasks
      ansible.builtin.import_tasks: tasks.yml

Here, Ansible imports the tasks defined in tasks.yml as part of the main playbook.

3. Understanding the Syntax

Component Purpose
import_tasks Imports tasks from another YAML file.
tasks.yml The file containing the tasks to import.
ansible.builtin The built-in Ansible collection containing the module.
tasks The main playbook section where imported tasks are declared.
Important: The imported file contains a list of tasks. It does not contain its own hosts, become, or tasks play structure.

4. Create a Separate Task File

Create a file named application_tasks.yml.

application_tasks.yml

---
- name: Create application directory
  ansible.builtin.file:
    path: /opt/import-demo
    state: directory
    mode: '0755'

- name: Create application configuration
  ansible.builtin.copy:
    dest: /opt/import-demo/app.conf
    content: |
      APP_NAME=ImportDemo
      APP_ENV=development
    mode: '0644'

- name: Create application log directory
  ansible.builtin.file:
    path: /opt/import-demo/logs
    state: directory
    mode: '0755'

This file contains three tasks that will be imported into the main playbook.

5. Import the Task File into the Main Playbook

Create a file named main.yml.

main.yml

---
- name: Configure application
  hosts: ansible-client
  become: true

  tasks:
    - name: Import application tasks
      ansible.builtin.import_tasks: application_tasks.yml

When Ansible processes the playbook, it incorporates the imported tasks into the play.

6. Execute the Playbook

Run the playbook from your Ansible controller:

ansible-playbook main.yml

To verify the result, create a separate playbook named verify.yml.

---
- name: Verify application configuration
  hosts: ansible-client
  become: true

  tasks:
    - name: Check application directory
      ansible.builtin.command: test -d /opt/import-demo
      changed_when: false

    - name: Check configuration file
      ansible.builtin.command: test -f /opt/import-demo/app.conf
      changed_when: false

    - name: Read application configuration
      ansible.builtin.command: cat /opt/import-demo/app.conf
      register: config_output
      changed_when: false

    - name: Display configuration
      ansible.builtin.debug:
        var: config_output.stdout

Execute the verification playbook:

ansible-playbook verify.yml

7. Import Multiple Task Files

You can import multiple task files into one playbook.

Example directory structure:

ansible-project/
├── main.yml
├── directories.yml
├── configuration.yml
└── permissions.yml

main.yml

---
- name: Configure application server
  hosts: ansible-client
  become: true

  tasks:
    - name: Import directory tasks
      ansible.builtin.import_tasks: directories.yml

    - name: Import configuration tasks
      ansible.builtin.import_tasks: configuration.yml

    - name: Import permission tasks
      ansible.builtin.import_tasks: permissions.yml

Ansible imports the task lists in the order they appear in the playbook.

8. Using Variables with import_tasks

You can use variables to provide values to tasks in the imported file.

main.yml

---
- name: Configure application
  hosts: ansible-client
  become: true

  vars:
    application_name: import-demo
    application_path: /opt/import-demo

  tasks:
    - name: Import application tasks
      ansible.builtin.import_tasks: application_tasks.yml

application_tasks.yml

---
- name: Create application directory
  ansible.builtin.file:
    path: "{{ application_path }}"
    state: directory
    mode: '0755'

- name: Create application information file
  ansible.builtin.copy:
    dest: "{{ application_path }}/info.txt"
    content: |
      Application: {{ application_name }}
    mode: '0644'

The imported tasks can access variables defined in the main play.

9. Using Conditions with import_tasks

You can apply a when condition to an imported task file.

---
- name: Conditional task import
  hosts: ansible-client
  become: true

  tasks:
    - name: Import Ubuntu tasks
      ansible.builtin.import_tasks: ubuntu_tasks.yml
      when: ansible_facts['distribution'] == "Ubuntu"

Important difference: With static imports, the condition is applied to each imported task. Each task evaluates the condition when it executes.

If a task changes a variable used by the condition, later imported tasks can evaluate that condition differently.

10. import_tasks vs include_tasks

Both methods allow you to organize tasks into separate files, but they work differently.

Feature import_tasks include_tasks
Type Static inclusion Dynamic inclusion
Processing Processed when Ansible loads the playbook Processed during playbook execution
Conditions Condition applies to each imported task Condition controls whether the file is included
Loops Cannot loop directly over an import_tasks statement Can loop over an include_tasks statement
Task visibility Imported tasks are visible during task listing Included tasks may not appear until execution
Remember: Use import_tasks when you want static task inclusion. Use include_tasks when you need dynamic inclusion, such as including a task file conditionally or repeatedly using a loop.

11. Practical Project: Modular Application Configuration

Objective

Build a modular playbook that creates an application directory, writes configuration, and creates a log directory using imported task files.

Directory structure:

import-project/
├── main.yml
├── directories.yml
├── config.yml
└── logs.yml

directories.yml

---
- name: Create application directory
  ansible.builtin.file:
    path: /opt/import-project
    state: directory
    mode: '0755'

config.yml

---
- name: Create application configuration
  ansible.builtin.copy:
    dest: /opt/import-project/application.conf
    content: |
      APPLICATION=LearningLabs
      ENVIRONMENT=lab
    mode: '0644'

logs.yml

---
- name: Create application log directory
  ansible.builtin.file:
    path: /opt/import-project/logs
    state: directory
    mode: '0755'

- name: Create initial log file
  ansible.builtin.copy:
    dest: /opt/import-project/logs/application.log
    content: "Application initialized\n"
    mode: '0644'

main.yml

---
- name: Deploy application structure
  hosts: ansible-client
  become: true

  tasks:
    - name: Import directory tasks
      ansible.builtin.import_tasks: directories.yml

    - name: Import configuration tasks
      ansible.builtin.import_tasks: config.yml

    - name: Import log tasks
      ansible.builtin.import_tasks: logs.yml

Execute:

ansible-playbook main.yml

Expected Result

The target Ubuntu container should contain:

/opt/import-project/
├── application.conf
└── logs/
    └── application.log

The configuration and log files should contain the content defined in their respective task files.

Why Do We Use Ansible import_tasks?

We use import_tasks to divide large playbooks into smaller, organized task files while keeping their execution structure predictable.

In real-world DevOps automation, a server deployment may require several operations, such as creating directories, installing dependencies, configuring applications, and setting permissions.

Instead of maintaining every task in one large playbook, we can place related tasks in separate files and statically import them into the main playbook.

This improves readability, maintainability, and code reuse. It also allows Ansible to process imported tasks before execution, making the task structure visible during playbook inspection.
