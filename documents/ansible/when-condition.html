Ansible When Condition

The Ansible when keyword is used to execute tasks conditionally. It allows a playbook to make decisions based on variables, facts, registered results and logical expressions.

1. What Is the When Keyword?

The when keyword is a conditional expression used to control whether an Ansible task should execute.

Ansible evaluates the condition before executing the task. If the condition evaluates to true, the task runs. If it evaluates to false, Ansible skips the task.

Common use cases include:

  • Executing tasks only on Ubuntu servers.
  • Installing packages based on operating system versions.
  • Running tasks based on variable values.
  • Executing tasks based on registered command results.
  • Checking available system resources.
  • Running different deployment tasks for development and production.
  • Skipping unnecessary tasks when a condition is not satisfied.

2. How Does When Work?

             Ansible Controller
             ------------------
                    |
                    v
                 Playbook
                    |
                    v
              Evaluate Condition
                    |
             +------+------+
             |             |
           TRUE          FALSE
             |             |
             v             v
        Execute Task     Skip Task
             |             |
             v             v
        Continue       Continue

Unlike an assertion failure, a false when condition normally skips the task without failing the play.

3. Basic When Syntax

The when keyword is written at the same indentation level as the module inside a task. 

---
- name: Basic when condition
  hosts: ansible-client
  become: true

  vars:
    application_environment: production

  tasks:
    - name: Display production message
      ansible.builtin.debug:
        msg: "Production environment detected."
      when: application_environment == "production"

The task executes only when the variable application_environment equals production.

4. Comparison Operators

You can use comparison operators to evaluate variable values.

Operator Meaning Example
== Equal to port == 8080
!= Not equal to environment != "testing"
> Greater than memory > 1024
< Less than memory < 2048
>= Greater than or equal to port >= 1024
<= Less than or equal to memory <= 4096
in Value exists in a list environment in supported
not in Value does not exist in a list environment not in disabled

5. Execute a Task When a Variable Matches

You can execute a task when a variable contains a specific value.

Playbook: when-variable.yml

---
- name: Execute task based on variable
  hosts: ansible-client
  become: true

  vars:
    environment: production

  tasks:
    - name: Display production configuration message
      ansible.builtin.debug:
        msg: "Applying production configuration."
      when: environment == "production"

    - name: Display development configuration message
      ansible.builtin.debug:
        msg: "Applying development configuration."
      when: environment == "development"

Only the task whose condition matches the variable value will execute. The other task will be skipped.

6. Execute a Task When a Variable Does Not Match

Use the != operator when a task should execute only if a variable does not match a particular value.

Playbook: when-not-equal.yml

---
- name: Check environment
  hosts: ansible-client
  become: true

  vars:
    environment: development

  tasks:
    - name: Display non-production warning
      ansible.builtin.debug:
        msg: "This is not a production environment."
      when: environment != "production"

7. Use Multiple Conditions with AND

When you provide multiple conditions as a YAML list under when, all conditions must be true. This is equivalent to logical AND.

Playbook: when-and.yml

---
- name: Validate deployment conditions
  hosts: ansible-client
  become: true

  vars:
    environment: production
    application_port: 8080

  tasks:
    - name: Execute production deployment task
      ansible.builtin.debug:
        msg: "Production deployment requirements satisfied."
      when:
        - environment == "production"
        - application_port == 8080

The task executes only when both conditions are true.

8. Use OR Conditions

Use the or operator when at least one condition must be true.

Playbook: when-or.yml

---
- name: Check supported environments
  hosts: ansible-client
  become: true

  vars:
    environment: testing

  tasks:
    - name: Display supported environment message
      ansible.builtin.debug:
        msg: "Environment is supported."
      when: >
        environment == "development" or
        environment == "testing"

The task executes if either condition evaluates to true.

9. Use NOT Conditions

The not operator reverses a Boolean condition.

Playbook: when-not.yml

---
- name: Check environment using NOT
  hosts: ansible-client
  become: true

  vars:
    maintenance_mode: false

  tasks:
    - name: Execute task when maintenance is disabled
      ansible.builtin.debug:
        msg: "Application is available for deployment."
      when: not maintenance_mode

10. Execute Tasks Based on Operating System Facts

Ansible gathers operating system information as facts. You can use these facts to execute tasks only on specific operating systems.

Playbook: when-os.yml

---
- name: Execute tasks based on operating system
  hosts: ansible-client
  become: true

  tasks:
    - name: Display Ubuntu information
      ansible.builtin.debug:
        msg: "Ubuntu operating system detected."
      when: ansible_distribution == "Ubuntu"

    - name: Display Debian information
      ansible.builtin.debug:
        msg: "Debian operating system detected."
      when: ansible_distribution == "Debian"

Ansible executes the matching task based on the detected distribution.

11. Execute Tasks Based on Memory

You can use system facts to control tasks based on memory requirements.

Playbook: when-memory.yml

---
- name: Check available system memory
  hosts: ansible-client
  become: true

  tasks:
    - name: Display high-memory message
      ansible.builtin.debug:
        msg: "Host has at least 2 GB of total memory."
      when: ansible_memtotal_mb >= 2048

    - name: Display low-memory message
      ansible.builtin.debug:
        msg: "Host has less than 2 GB of total memory."
      when: ansible_memtotal_mb < 2048

The fact ansible_memtotal_mb represents total detected memory, not currently available memory.

12. Use When with Register

One of the most useful applications of when is combining it with register.

A task captures command output, and another task executes only when the registered result satisfies a condition.

Playbook: when-register.yml

---
- name: Check application directory
  hosts: ansible-client
  become: true

  tasks:
    - name: Check whether application directory exists
      ansible.builtin.command:
        cmd: test -d /tmp/learning-labs
      register: directory_result
      changed_when: false
      failed_when: false

    - name: Display directory exists message
      ansible.builtin.debug:
        msg: "Application directory exists."
      when: directory_result.rc == 0

    - name: Display directory missing message
      ansible.builtin.debug:
        msg: "Application directory does not exist."
      when: directory_result.rc != 0

The first task captures the command return code. The remaining tasks use that result to decide which message to display.

13. Check Whether a Variable Is Defined

The is defined test checks whether a variable exists before a task attempts to use it.

Playbook: when-defined.yml

---
- name: Check variable definition
  hosts: ansible-client
  become: true

  vars:
    application_name: learning-labs

  tasks:
    - name: Display application name
      ansible.builtin.debug:
        msg: "Application: {{ application_name }}"
      when: application_name is defined

You can also use is not defined to check whether a variable is missing. 

---
- name: Check missing variable
  hosts: ansible-client
  become: true

  tasks:
    - name: Display missing variable message
      ansible.builtin.debug:
        msg: "Application name was not provided."
      when: application_name is not defined

14. Check Boolean Variables

When a variable contains a Boolean value, you can check whether it is true or false.

Playbook: when-boolean.yml

---
- name: Check Boolean variable
  hosts: ansible-client
  become: true

  vars:
    enable_monitoring: true

  tasks:
    - name: Configure monitoring
      ansible.builtin.debug:
        msg: "Monitoring is enabled."
      when: enable_monitoring

    - name: Skip monitoring configuration
      ansible.builtin.debug:
        msg: "Monitoring is disabled."
      when: not enable_monitoring

15. Use When with a List of Values

The in operator checks whether a value exists inside a list.

Playbook: when-list.yml

---
- name: Validate supported environment
  hosts: ansible-client
  become: true

  vars:
    environment: testing
    supported_environments:
      - development
      - testing
      - production

  tasks:
    - name: Check supported environment
      ansible.builtin.debug:
        msg: "Environment is supported."
      when: environment in supported_environments

    - name: Check unsupported environment
      ansible.builtin.debug:
        msg: "Environment is not supported."
      when: environment not in supported_environments

16. Use When with a Loop

You can use when with a loop to execute a task only for matching loop items.

Playbook: when-loop.yml

---
- name: Process selected environments
  hosts: ansible-client
  become: true

  vars:
    environments:
      - development
      - testing
      - production

  tasks:
    - name: Display production environment
      ansible.builtin.debug:
        msg: "Processing {{ item }}"
      loop: "{{ environments }}"
      when: item == "production"

Ansible evaluates the condition for each loop item. Only the matching item executes the task.

17. When with String Tests

Jinja2 provides useful tests for checking string values.

Test Purpose
is defined Checks whether a variable exists.
is undefined Checks whether a variable does not exist.
is string Checks whether a value is a string.
is integer Checks whether a value is an integer.
is boolean Checks whether a value is a Boolean.
is true Checks whether a value is Boolean true.
is false Checks whether a value is Boolean false.

Playbook: when-data-type.yml

---
- name: Validate variable types
  hosts: ansible-client
  become: true

  vars:
    application_name: learning-labs
    application_port: 8080

  tasks:
    - name: Validate application name type
      ansible.builtin.debug:
        msg: "Application name is a string."
      when: application_name is string

    - name: Validate application port type
      ansible.builtin.debug:
        msg: "Application port is an integer."
      when: application_port is integer

18. Important Considerations

  • when is a playbook keyword, not a module.
  • Do not use {{ }} around expressions in a when condition.
  • Multiple conditions in a YAML list are evaluated using AND logic.
  • Use or when any one condition can satisfy the requirement.
  • Use not to reverse a Boolean condition.
  • Facts must be gathered before using fact variables.
  • Registered variables can be used in subsequent task conditions.
  • A false condition normally results in a skipped task, not a failed play.
  • Ensure variable types are correct before performing numeric comparisons.
  • Conditions are evaluated separately for each managed host.

19. Practical Project: Environment-Based Deployment Validation

Project Objective

Create a playbook that evaluates deployment settings and executes different tasks depending on the target environment and system facts.

Requirements:
  1. Define an application environment variable.
  2. Validate whether the environment is supported.
  3. Execute a production-specific task for production.
  4. Execute a development-specific task for development.
  5. Check whether monitoring is enabled.
  6. Check whether the managed host is Ubuntu.
  7. Display a message when the environment is unsupported.
Project playbook: environment-deployment.yml 
---
- name: Environment-based deployment
  hosts: ansible-client
  become: true

  vars:
    application_name: learning-labs
    deployment_environment: production
    enable_monitoring: true

    supported_environments:
      - development
      - testing
      - production

  tasks:
    - name: Validate deployment environment
      ansible.builtin.assert:
        that:
          - deployment_environment in supported_environments
        success_msg: "Deployment environment is supported."
        fail_msg: "Unsupported deployment environment."

    - name: Display application information
      ansible.builtin.debug:
        msg: "Preparing {{ application_name }} deployment."

    - name: Execute production preparation
      ansible.builtin.debug:
        msg: "Preparing production deployment."
      when: deployment_environment == "production"

    - name: Execute development preparation
      ansible.builtin.debug:
        msg: "Preparing development deployment."
      when: deployment_environment == "development"

    - name: Execute testing preparation
      ansible.builtin.debug:
        msg: "Preparing testing deployment."
      when: deployment_environment == "testing"

    - name: Configure monitoring
      ansible.builtin.debug:
        msg: "Monitoring configuration is enabled."
      when: enable_monitoring

    - name: Display Ubuntu information
      ansible.builtin.debug:
        msg: "Ubuntu target detected."
      when: ansible_distribution == "Ubuntu"

Why Do We Use the Ansible When Keyword?

In real-world DevOps environments, not every task should execute on every server. Different servers may have different operating systems, application environments, resource requirements and configuration settings.

For example, a production deployment may require different configuration from a development deployment. Similarly, a task that is specific to Ubuntu should not execute on a different operating system.

The When keyword allows engineers to introduce decision-making into automation. It evaluates conditions and determines whether a task should execute or be skipped.

It is commonly used in multi-environment deployments, operating system-specific automation, infrastructure provisioning and conditional configuration management.
