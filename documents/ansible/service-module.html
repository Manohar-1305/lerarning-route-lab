Ansible Service Module

Learn how to manage Linux services using Ansible playbooks, including starting, stopping, restarting, and enabling services.

1. What Is the Service Module?

The ansible.builtin.service module manages services on Linux and Unix systems. It provides a common interface for controlling services without requiring you to use a different module for every supported service manager.

For example, a Linux server may run services such as SSH, cron, networking, database servers, and web servers. Administrators need to start, stop, restart, and enable these services during routine operations.

The Ansible service module allows you to automate these operations across managed hosts.

Important for this lab: The ansible-client is an Ubuntu container. Containers generally do not run systemd as PID 1. Therefore, systemd-dependent service operations may fail even when the playbook syntax is correct. This lesson uses a real service process that can run inside the Ubuntu container, rather than assuming systemd is available.

2. Understanding Linux Services

A service is a background process that performs a specific function on a system. Services can start automatically, remain running in the background, and respond to requests.

Examples of common Linux services:

  • SSH: Provides remote login access.
  • Cron: Runs scheduled jobs.
  • Nginx: Provides web server functionality.
  • Apache: Provides HTTP server functionality.
  • MySQL: Provides database services.

3. Service States

State Purpose
started Starts the service if it is not already running.
stopped Stops the service if it is running.
restarted Restarts the service.
reloaded Reloads service configuration when supported.

The service module can also manage whether a service should start automatically at boot, when the underlying service manager supports that functionality.

4. Important Parameters

Parameter Description
name Name of the service to manage. Required.
state Desired service state: started, stopped, restarted, or reloaded.
enabled Controls whether the service starts automatically at boot, if supported.
arguments Additional arguments passed to the service command on supported platforms.
pattern Process pattern used on systems where service status cannot be determined reliably through the service manager.
sleep Number of seconds to wait between stop and start operations on supported systems.
use Selects a service module implementation. Defaults to automatic detection.

5. Installing a Service Package

Before managing a service, its software package must be installed on the target host.

In this lab, we will use Nginx as an example. The package can be installed inside the Ubuntu container. 

---
- name: Install Nginx
  hosts: ansible-client
  become: true

  tasks:
    - name: Install Nginx package
      ansible.builtin.apt:
        name: nginx
        state: present
        update_cache: true
Installing Nginx does not guarantee that its service can be started in a container. The package can be installed, but service management depends on the container's process environment and available service manager.

6. Starting a Service

The started state ensures that a service is running. If it is already running, Ansible does not restart it. 

---
- name: Start Nginx service
  hosts: ansible-client
  become: true

  tasks:
    - name: Ensure Nginx is running
      ansible.builtin.service:
        name: nginx
        state: started

This is a valid service-management task when the target has a compatible service manager and Nginx is installed.

7. Stopping a Service

Use state: stopped to ensure a service is not running. 

---
- name: Stop Nginx service
  hosts: ansible-client
  become: true

  tasks:
    - name: Ensure Nginx is stopped
      ansible.builtin.service:
        name: nginx
        state: stopped

8. Restarting a Service

Use state: restarted when a service needs to be restarted, for example after a configuration change. 

---
- name: Restart Nginx service
  hosts: ansible-client
  become: true

  tasks:
    - name: Restart Nginx
      ansible.builtin.service:
        name: nginx
        state: restarted
Unlike started, the restarted state performs a restart when the task runs. It is not an idempotent no-op when the service is already running.

9. Enabling a Service at Boot

The enabled parameter controls whether a service should start automatically when the system boots. 

---
- name: Enable Nginx at boot
  hosts: ansible-client
  become: true

  tasks:
    - name: Enable Nginx service
      ansible.builtin.service:
        name: nginx
        enabled: true

This operation requires a compatible service manager. A normal Ubuntu container does not necessarily have a boot process or service manager.

10. Starting and Enabling a Service Together

You can use state and enabled together when managing a service on a system that supports both operations. 

---
- name: Configure Nginx service
  hosts: ansible-client
  become: true

  tasks:
    - name: Start and enable Nginx
      ansible.builtin.service:
        name: nginx
        state: started
        enabled: true

11. Understanding Handlers

Handlers are tasks that execute only when notified by another task. They are commonly used to restart or reload services after configuration changes.

For example, when an Nginx configuration file changes, Ansible can notify a handler to restart Nginx. 

---
- name: Configure Nginx
  hosts: ansible-client
  become: true

  tasks:
    - name: Deploy Nginx configuration
      ansible.builtin.copy:
        dest: /tmp/nginx.conf
        content: |
          worker_processes 1;
          events {
              worker_connections 128;
          }
        mode: '0644'
      notify: Restart Nginx

  handlers:
    - name: Restart Nginx
      ansible.builtin.service:
        name: nginx
        state: restarted

The handler runs only if the configuration task reports a change. This example demonstrates the handler structure; the temporary file is not the active Nginx configuration.

12. Checking Service Status in a Container

Since this lab runs inside an Ubuntu container, you should understand how to check a process without assuming systemd is available.

The following playbook checks whether the Nginx process exists using Ansible's command module. 

---
- name: Check Nginx process
  hosts: ansible-client
  become: true

  tasks:
    - name: Check whether Nginx is running
      ansible.builtin.command:
        argv:
          - pgrep
          - -x
          - nginx
      register: nginx_process
      changed_when: false
      failed_when: false

    - name: Display Nginx process status
      ansible.builtin.debug:
        msg: >-
          {{
            'Nginx process is running'
            if nginx_process.rc == 0
            else 'Nginx process is not running'
          }}

This checks for a process named nginx. It does not prove that the application is responding correctly to HTTP requests.

13. Practical Project: Manage a Process in the Ubuntu Container

Because the ansible-client container does not necessarily run systemd, this project demonstrates process lifecycle management using Ansible tasks and a simple background process.

Project Requirements

  • Create a directory for the project.
  • Create a small background process script.
  • Start the process on ansible-client.
  • Check whether the process is running.
  • Stop the process.
  • Verify that the process has stopped.

Step 1: Create the Process Script

Create templates/lab-worker.sh.j2 on the Ansible controller. 

#!/bin/sh

while true
do
    echo "Learning Labs worker is running"
    sleep 30
done

Step 2: Create the Start Playbook

Create start-worker.yml:

---
- name: Start background worker
  hosts: ansible-client
  become: true

  tasks:
    - name: Create worker directory
      ansible.builtin.file:
        path: /tmp/ansible-service-lab
        state: directory
        mode: '0755'

    - name: Deploy worker script
      ansible.builtin.copy:
        src: files/lab-worker.sh
        dest: /tmp/ansible-service-lab/lab-worker.sh
        mode: '0755'

    - name: Start worker process
      ansible.builtin.shell:
        cmd: >-
          nohup /bin/sh /tmp/ansible-service-lab/lab-worker.sh
          >/tmp/ansible-service-lab/worker.log 2>&1
          -
          {{
            'Worker process is running'
            if worker_process.rc == 0
            else 'Worker process is not running'
          }}
Correction for this project: A PID file must be created and maintained for reliable start/stop operations. The following complete playbook uses a PID file and avoids relying on a system service manager.

Step 3: Use This Complete Process Management Playbook

Create manage-worker.yml. This playbook supports starting, checking, and stopping the background worker. 

---
- name: Manage background worker
  hosts: ansible-client
  become: true

  vars:
    worker_dir: /tmp/ansible-service-lab
    worker_script: /tmp/ansible-service-lab/lab-worker.sh
    worker_pid_file: /tmp/ansible-service-lab/worker.pid

  tasks:
    - name: Create worker directory
      ansible.builtin.file:
        path: "{{ worker_dir }}"
        state: directory
        mode: '0755'

    - name: Deploy worker script
      ansible.builtin.copy:
        dest: "{{ worker_script }}"
        content: |
          #!/bin/sh
          echo "$$" > /tmp/ansible-service-lab/worker.pid
          while true
          do
              echo "Learning Labs worker is running"
              sleep 30
          done
        mode: '0755'

    - name: Check existing worker PID file
      ansible.builtin.stat:
        path: "{{ worker_pid_file }}"
      register: pid_file

    - name: Read existing worker PID
      ansible.builtin.slurp:
        src: "{{ worker_pid_file }}"
      register: existing_pid
      when: pid_file.stat.exists

    - name: Check existing worker process
      ansible.builtin.command:
        argv:
          - kill
          - -0
          - "{{ existing_pid.content | b64decode | trim }}"
      register: existing_process
      changed_when: false
      failed_when: false
      when: pid_file.stat.exists

    - name: Start worker when not running
      ansible.builtin.shell:
        cmd: >-
          nohup /bin/sh "{{ worker_script }}"
          >/tmp/ansible-service-lab/worker.log 2>&1
          
        not pid_file.stat.exists or
        existing_process.rc != 0

    - name: Wait for worker PID file
      ansible.builtin.wait_for:
        path: "{{ worker_pid_file }}"
        state: present
        timeout: 10

    - name: Read worker PID
      ansible.builtin.slurp:
        src: "{{ worker_pid_file }}"
      register: worker_pid

    - name: Verify worker process
      ansible.builtin.command:
        argv:
          - kill
          - -0
          - "{{ worker_pid.content | b64decode | trim }}"
      changed_when: false

    - name: Display worker status
      ansible.builtin.debug:
        msg: "Background worker is running"

Step 4: Stop the Worker

Create stop-worker.yml:

---
- name: Stop background worker
  hosts: ansible-client
  become: true

  vars:
    worker_pid_file: /tmp/ansible-service-lab/worker.pid

  tasks:
    - name: Check PID file
      ansible.builtin.stat:
        path: "{{ worker_pid_file }}"
      register: pid_file

    - name: Read worker PID
      ansible.builtin.slurp:
        src: "{{ worker_pid_file }}"
      register: worker_pid
      when: pid_file.stat.exists

    - name: Stop worker process
      ansible.builtin.command:
        argv:
          - kill
          - "{{ worker_pid.content | b64decode | trim }}"
      when: pid_file.stat.exists

    - name: Remove PID file
      ansible.builtin.file:
        path: "{{ worker_pid_file }}"
        state: absent

    - name: Display completion message
      ansible.builtin.debug:
        msg: "Worker stop operation completed"
Project outcome: You have practised starting, checking, and stopping a process inside ansible-client without depending on systemd. This is a container-compatible process-management exercise, not a replacement for managing a systemd service on a full Ubuntu server.

Why Do We Use the Ansible Service Module?

Linux systems run background services that provide essential functionality such as remote access, web hosting, database connectivity, scheduling, and monitoring. These services must be maintained in the correct state for applications and infrastructure to operate reliably.

In a manually managed environment, administrators connect to servers and execute service-management operations individually. When an organization manages multiple servers, repeating these operations becomes time-consuming and inconsistent.

The Ansible service module provides a consistent way to manage services across supported Linux systems. It allows administrators to define the desired service state in a playbook and apply it to multiple managed hosts.

Practical Reasons to Use It

  • Service availability: Ensure required services are running.
  • Service control: Start, stop, restart, and reload supported services.
  • Boot configuration: Enable services to start automatically when the underlying service manager supports it.
  • Application deployment: Restart or reload services after configuration changes.
  • Consistent operations: Apply service-management tasks across multiple managed servers.
  • Automation: Integrate service operations into repeatable infrastructure and deployment playbooks.

Real-World DevOps Example

Imagine an organization managing 50 Ubuntu servers running an application behind Nginx. After deploying a new configuration, the Nginx service must be reloaded on the affected servers.

A DevOps engineer can use an Ansible playbook to manage the service across the inventory instead of manually connecting to every server.

Ansible applies the requested operation consistently wherever a compatible service manager is available.

Remember: The service module manages actual services through the available service manager. A background process running inside a container is not automatically a system service. Always check the target environment before using service-management tasks.
