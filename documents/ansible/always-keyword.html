Ansible always Keyword

The always section allows you to execute tasks after the normal block and rescue execution paths. It is commonly used for final status messages, cleanup operations, and recording execution information.

1. What Is always?

In Ansible, always is used with a block to define tasks that should execute after the block and its applicable rescue section.

Unlike normal tasks, which stop executing when a task fails, the always section provides a separate execution path for final operations.

For example, an application deployment may involve:

  • Creating application directories.
  • Copying configuration files.
  • Validating the deployment.
  • Recording the final execution status.

Even if an operation fails, you may still want to record information about the deployment attempt.

2. Basic Syntax

---
- name: Demonstrate always
  hosts: ansible-client
  become: true

  tasks:
    - name: Application operation
      block:
        - name: Execute normal task
          ansible.builtin.debug:
            msg: "Normal task executed"

      always:
        - name: Execute final task
          ansible.builtin.debug:
            msg: "Always section executed"

The always section is defined at the same indentation level as block and rescue.

3. Understanding Execution Flow

Consider a block containing a normal task and an always task. 

---
- name: Demonstrate execution flow
  hosts: ansible-client
  become: true

  tasks:
    - name: Application operation
      block:
        - name: First task
          ansible.builtin.debug:
            msg: "First task executed"

        - name: Second task
          ansible.builtin.debug:
            msg: "Second task executed"

      always:
        - name: Final task
          ansible.builtin.debug:
            msg: "Always task executed"

The execution order is:

Order Task Result
1 First task Executed
2 Second task Executed
3 Always task Executed

The always section executes after the normal block tasks complete.

4. Execute always When a Block Fails

One of the most useful features of always is that it can execute even when a task inside the block fails. 

---
- name: Demonstrate always after failure
  hosts: ansible-client
  become: true

  tasks:
    - name: Application operation
      block:
        - name: First task
          ansible.builtin.debug:
            msg: "First task executed"

        - name: Failing task
          ansible.builtin.command:
            cmd: /bin/false

        - name: Third task
          ansible.builtin.debug:
            msg: "This task will be skipped"

      always:
        - name: Final execution message
          ansible.builtin.debug:
            msg: "Always section executed after failure"

The execution flow is:

  1. The first task executes successfully.
  2. The second task fails.
  3. The third normal task is skipped.
  4. The always section executes.
Important: The always section does not convert the original failure into success. The play remains failed unless the failure is successfully handled by a rescue section.

5. Execute always After Successful Recovery

You can use always together with block and rescue.

In this arrangement:

  • block contains normal operations.
  • rescue contains recovery operations.
  • always contains final operations.
---
- name: Demonstrate block rescue always
  hosts: ansible-client
  become: true

  tasks:
    - name: Application deployment
      block:
        - name: Execute deployment
          ansible.builtin.command:
            cmd: /bin/false

      rescue:
        - name: Handle deployment failure
          ansible.builtin.debug:
            msg: "Deployment failure handled"

      always:
        - name: Record final execution
          ansible.builtin.debug:
            msg: "Final execution section completed"

The execution order is:

Order Section Execution
1 block Deployment task fails
2 rescue Recovery task executes
3 always Final task executes

Because the rescue task succeeds, Ansible considers the original failure handled and can continue with subsequent tasks.

6. Use always for Cleanup Operations

A common use case is removing temporary files created during automation.

For example, a deployment process may create a temporary file. You can remove it in the always section. 

---
- name: Temporary file cleanup
  hosts: ansible-client
  become: true

  tasks:
    - name: Application deployment
      block:
        - name: Create temporary file
          ansible.builtin.copy:
            content: "Temporary deployment data\n"
            dest: /tmp/deployment-temp.conf
            mode: '0600'

        - name: Execute deployment validation
          ansible.builtin.command:
            cmd: test -f /tmp/deployment-temp.conf
          changed_when: false

      always:
        - name: Remove temporary file
          ansible.builtin.file:
            path: /tmp/deployment-temp.conf
            state: absent

        - name: Display cleanup result
          ansible.builtin.debug:
            msg: "Temporary file cleanup completed"

The temporary file is removed after the block execution, whether the normal tasks succeed or an ordinary task failure occurs.

Important: Always is not an unconditional guarantee against every possible failure. Unreachable hosts, invalid task definitions, and other execution interruptions can prevent tasks from running. Cleanup tasks themselves can also fail.

7. Use always to Record Execution Information

You can use the always section to record when an automation workflow reaches its final stage. 

---
- name: Record application execution
  hosts: ansible-client
  become: true

  tasks:
    - name: Application operation
      block:
        - name: Create application directory
          ansible.builtin.file:
            path: /opt/learning-labs
            state: directory
            mode: '0755'

        - name: Validate application directory
          ansible.builtin.command:
            cmd: test -d /opt/learning-labs
          changed_when: false

      always:
        - name: Record execution timestamp
          ansible.builtin.command:
            cmd: date
          register: execution_time
          changed_when: false

        - name: Display execution timestamp
          ansible.builtin.debug:
            msg: "Execution reached final stage at {{ execution_time.stdout }}"

The timestamp command executes in the always section after the block's normal execution path.

8. Difference Between block, rescue, and always

Keyword Purpose
block Groups normal tasks together.
rescue Executes recovery tasks when a block task fails.
always Executes final tasks after the block and applicable rescue execution.

These three sections are often used together to create structured error-handling workflows.

9. What Happens When always Fails?

The always section contains normal Ansible tasks. If a task inside always fails, Ansible treats that failure normally. 

---
- name: Demonstrate always failure
  hosts: ansible-client
  become: true

  tasks:
    - name: Application operation
      block:
        - name: Normal task
          ansible.builtin.debug:
            msg: "Block executed"

      always:
        - name: Failing cleanup task
          ansible.builtin.command:
            cmd: /bin/false

    - name: Final playbook task
      ansible.builtin.debug:
        msg: "This task will not execute after the always failure"

The block succeeds, but the always task fails. The final task is not executed for that host because the play has encountered an unhandled failure.

10. Important Rules About always

  • always is associated with a block.
  • It executes after normal block execution.
  • It also executes after applicable rescue execution.
  • It is useful for cleanup and final reporting.
  • It does not automatically recover the original failure.
  • Tasks inside always can also fail.
  • It cannot guarantee execution if the host becomes unreachable or execution is interrupted.

11. Practical Lab: Application Deployment With Cleanup

Scenario

You are preparing an application deployment. The playbook must:

  • Create a temporary configuration file.
  • Execute a validation task.
  • Handle validation failure using rescue.
  • Remove the temporary file using always.
  • Display the final cleanup message.

Create this playbook:

---
- name: Application deployment with cleanup
  hosts: ansible-client
  become: true

  tasks:
    - name: Application deployment workflow
      block:

        - name: Create temporary configuration
          ansible.builtin.copy:
            content: |
              APPLICATION_NAME=learning-labs
              APPLICATION_PORT=8080
            dest: /tmp/learning-labs-temp.conf
            mode: '0600'

        - name: Validate configuration
          ansible.builtin.command:
            cmd: test -f /tmp/learning-labs-temp.conf
          changed_when: false

        - name: Execute deployment check
          ansible.builtin.command:
            cmd: /bin/false

      rescue:

        - name: Record deployment failure
          ansible.builtin.copy:
            content: "Application deployment failed\n"
            dest: /tmp/learning-labs-failure.log
            mode: '0644'

        - name: Display recovery message
          ansible.builtin.debug:
            msg: "Failure information recorded"

      always:

        - name: Remove temporary configuration
          ansible.builtin.file:
            path: /tmp/learning-labs-temp.conf
            state: absent

        - name: Display cleanup completion
          ansible.builtin.debug:
            msg: "Temporary configuration cleanup completed"

    - name: Display final workflow status
      ansible.builtin.debug:
        msg: "Application workflow completed"

Run from ansible-controller:

ansible-playbook application-always.yml

Expected behavior:

  • The temporary configuration file is created.
  • The configuration validation succeeds.
  • The deployment check fails.
  • The rescue section records the failure.
  • The always section removes the temporary configuration.
  • The cleanup completion message is displayed.
  • The final workflow status task executes because rescue succeeded.

To test a successful block execution, replace /bin/false with /bin/true. The rescue section will be skipped, but the always section will still execute.

Why Do We Use the Ansible always Keyword?

In real DevOps environments, automation workflows often create temporary resources, generate logs, prepare deployment files, or perform operations that require final cleanup.

If a deployment task fails, normal task execution may stop. However, some operations should still be attempted, such as removing temporary files, recording execution details, or displaying a final status message.

The always keyword provides a dedicated section for these final operations. It executes after the normal block tasks and applicable rescue tasks, regardless of whether the block completed successfully or encountered an ordinary task failure.

When combined with block and rescue, it provides a structured approach to automation: normal execution, failure recovery, and final operations.

This is particularly useful in application deployments, infrastructure provisioning, configuration management, and other workflows where cleanup and execution reporting are important.
